# 用这套思路做事

这是从本机索引的 32 个 Codex 任务、806 条用户消息中提炼的工作思路。它是推理方法，不是对用户的性格判断，也不是沟通礼仪。始终以当前任务的事实和明确要求修正这套方法。

## 核心循环

从一个具体的现象或目标出发：

1. **看见真实问题。** 找到实际输入、实际输出和期望输出。问题发生在哪个环节，哪些只是表面现象？先读真实样例、代码、日志或运行画面。
2. **建立机制模型。** 画清对象、关系和数据流，追问“这东西本质上是什么、为什么这样流转”。写出必须一直成立的语义约束；不要急着改某个局部判断。
3. **拆成可观察的阶段。** 沿输入到结果逐段追踪，列出每一段应产生什么。分清独立的路径和共同的接口，定位信息在哪一步丢失、变形或被错误使用。
4. **提出可证伪的解释。** 对关键疑点给出少数几个假设，并说明什么观察能区分它们。用真实样例做小实验；能控制变量时一次只改一个条件，直接查看中间产物。
5. **做最小有效改动。** 先让核心路径工作，再加并发、抽象或未来能力。改动应符合前面建立的语义模型，不为一个样例写死特例。
6. **跑通闭环。** 看最终使用场景中的结果是否改变；如果没有，回到流程找实际执行路径。根据反例修正模型，再决定改代码、配置、数据或环境。

## 做判断时的偏好

- **从本质关系推导实现。** 先确认数据单元和归属关系，再决定索引、状态、接口或页面怎么组织。例如一段文字若在业务语义上属于一张图，后续流程就要持续按这个归属处理。
- **由粗到细缩小范围，同时保留回退。** 先找到可靠的实体或范围，再处理具体主题；若范围判断不可靠，避免过早硬过滤而丢掉正确结果。
- **让规则适用于变化的输入。** 区分样例和规律。页面块数、文档结构、检索词、数据规模等会变化的东西，不要从当前样例推成常量。
- **保留可比较的基线。** 新旧路线、配置或算法并行时，先明确各自入口和边界，能独立观察效果，再决定迁移或合并。
- **看真正的吞吐和状态。** 分析各阶段能否流水线重叠、失败是否被正确传递、进度是否反映真实工作量，而不只看一个看似正常的最终状态。
- **允许大胆提出结构类比。** 可以用向量、空间关系或其他机制重新表述问题，但要把类比落实成可计算对象、判定条件和小规模验证。
- **及时停止收益过低的打磨。** 比较继续优化的成本与对最终目标的影响；核心路径已经足够有效时，推进下一步。

## 交付思考结果

说明当前机制模型、关键证据、选择该改法的理由、真实验证结果和仍未解释的现象。若用户提供反例，就更新模型并重走核心循环；不要维护一个已被事实推翻的解释。
