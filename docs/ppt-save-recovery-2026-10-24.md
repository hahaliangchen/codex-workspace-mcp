# PPT 保存重试与失败恢复修复

日期：2026-10-24。本次只修改 PPT 服务端和前端，没有增加通用 Agent 的业务判断，没有运行真实 AI/PPT 生成。

## 修复行为

- **服务端同内容重试**：`ai-ppt-server/service/ppt_runtime/object_deck.go` 的重复保存判断保留 `revision == expected + 1` 和文件 SHA256 一致两个条件，去掉 `source` 一致条件。Agent 已经提交但没收到成功确认时，页面通过 user 入口提交同一份内容可以取得已经保存的版本，不新增对象、不增加历史版本，也不改写原保存来源。
- **前端保存确认**：`ai-ppt-view/src/api/pptDeck.ts` 遇到非 409 保存失败后立即重试一次。两次使用同一个 Blob、相同 expected_revision 和 source，不重新导出文件，不覆盖未知新版本。成功后返回已确认版本；首次错误作为 `save_recovery` 随该次工具结果传给 Agent。两次均失败时报告“保存结果未确认”并保留两次错误。409 不自动重试，仍进入冲突选择流程。
- **只读工具不受保存故障阻塞**：`DeckEditor.tsx` 通过 `utils/deckToolSave.ts` 运行本地工具。冲突或保存错误状态下，页面读取、渲染与布局检查仍可以读取本地稿件，不再因每次读取先保存而被同一错误挡住。保存状态放进工具的 JSON 正文，确保宿主转发后模型仍可见；冲突记录包含本地基准版本、已知服务端版本和需要用户选择的说明。图片结果保留图片并附加状态正文。
- **真正冲突仍禁止改稿**：冲突状态下，在调用修改工具之前拒绝执行；需要保存前置状态的修改，如果保存没有确认成功，也不继续应用新修改。本地只读结果标明当前未稳定保存，不能当成已保存版本的验收证据。

前端 `PptWorkflowStore` 的页面工具通道只补充该次保存恢复的事实，下一次工具结果不会重复携带先前错误。没有修改任务循环和完成检查逻辑。本次未修改字体越界容差。
