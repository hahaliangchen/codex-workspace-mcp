## 尚需修复

### 1. [P1] 已解决的历史失败仍被列为剩余问题

位置：`src/work_scheduler.rs:2373–2385`。

`execution_narrative` 的 `Remaining limitations` 扫描所有未废弃的已完成任务，把它们的 `limitations` 和 `expectation_met=false` 直接追加，没有判断这些问题是否已被后续结果解决。

例如 A 探测字体接口失败，以 `blocked` 或 `expectation_met=false` 返回；B 启动服务后同一接口返回 200。当前 HTTP 事实正确显示成功，但文本结尾仍出现 A 的“条件未满足”或“服务无法连接”。组织者被要求优先读这段文本，便又得到互相冲突的当前结论。

修复要求：旧限制留在对应步骤的历史结果中。只有仍有效的限制才能进入剩余问题；已明确被同一资源的新事实解决的旧失败要标注解决关系。无法确定是否解决的自由文本应标为“该步骤当时报告的限制”，不能自动升级成当前待办。不要通过废弃一个正确返回的旧任务来消除历史失败。

验收要求：A 连接失败 → B 同 URL 200 后，历史保留 A 的失败，当前事实成功，剩余问题不得仍列该连接失败。现有 `narrative_keeps_failure_then_recovery...` 使用 output 任务且没有设置失败限制/负面返回，尚未覆盖这个分支。

### 2. [P1] Observer 仍主要在派单、交接和重复读取时收到评估输入

位置：`src/agent_service.rs:3574–3591、4020–4025、4065–4082`；`src/observer_service.rs:614–631`。

普通 `report_progress` 写入 Worker 事件和节点状态，但没有推送 `observer.progress`。正常工具执行只有在重复查询/重叠读取/复用 HTTP 时才推送该输入。轮末虽然更新 `scope` 并 notify，但没有普通进度观察记录；Observer 循环只消费已有 pending 边界记录或 progress 槽，不会仅凭新的 scope 自动生成一份当前事实评估。

因此已取到的边界输入包含更完整的事实，但执行中的正常进展仍没有持续送达评估链路。一个长节点内出现“失败 → 启动成功 → 下一动作”时，Observer 可能仍在评估最初的派单快照，直到发生交接或被认定重复读取。

修复要求：每轮目的与动作结果持久化后，提交当前节点最新事实的进度快照。模型评估允许合并、节流；触发条件应包含有意义的结果变化，不能仅依赖重复读取。待评估输入要能更新为最新版本，而不只是更新用于实例有效性判断的 scope。

验收要求：同一节点中，正常请求失败后正常启动成功，即使没有重复工具调用且尚未 yield，Observer 最新输入也含成功状态和对应采样时间。

### 3. [P1] 正常的无 expect_text 页面读取会丢掉已确认页面状态

位置：`src/work_scheduler.rs:1720、1729–1731、2245–2259`；`src/browser_control.rs:95、207–209`。

`browser_read({})` 是合法调用；工具仍返回 `document_loaded`、上传关联和页码，`matched` 也为 true。但调度器每次读取先清掉 `browser_current_read`，然后只有非空 `expect_text` 才重新保存。

同一节点先通过带 expect_text 的读取确认加载，随后调用 `browser_read({})` 检查控件，会清掉原确认且不保存本次真实加载结果。当前浏览器事实可退化为“已上传但没有后续读取确认”；requires_pptx 的完成判定也可能不再通过，从而引出多余确认或重传。

修复要求：保存宿主页面/文稿事实与检查某个期望文本的结果分开。合法读取中的明确关联、loaded 和页码必须进入当前资源事实；expect_text 只决定该文本断言是否满足。未知结果不能伪造 loaded，但明确结果也不能因没指定文本而丢失。

验收要求：上传 → 带文本确认 loaded → 无文本读取控件，当前事实仍正确记录最新读取的 loaded、页码、上传 ID。

### 4. [P1] Worker 流解析记录了断流，却未拒绝执行其工具

位置：`src/agent_service.rs:1774–1780`；`src/work_executor.rs:140–145、176–180`；`src/model_stream.rs:307–310`。

共享累加器在缺少 DONE/finish_reason 的 EOF 下返回 `terminated=false`。Organizer 会拒绝这样的响应，Worker 却只是把该标志写入 stats，继续取出工具调用、将请求标为 completed 并执行。Worker 同样没有检查 length/content_filter。

如果连接在一个可解析工具参数生成后、正式终止信号前结束，Worker 仍可能执行写文件/启动进程等动作；工具参数不完整时还可能走默认参数和反复修正路径。这是代码路径允许的风险，本次没有实测触发。

修复要求：Worker 执行任何工具前采用完整响应终止校验；拒绝不完整 EOF 和非正常终止，保留部分指标，将请求标为失败。保留完整 JSON 响应兼容路径，不要把其没有 SSE DONE 当作错误。

验收要求：完整工具 JSON 后直接 EOF，无 DONE/finish_reason，工具执行次数为 0；length/content_filter 不执行副作用；正常完成仍执行一次。

### 5. [P2] HTTP 与服务启动的时间关系没有绑定具体服务

位置：`src/work_scheduler.rs:2187–2203、1443–1445`。

`service_observed_running_at` 取所有任务里“任意受管进程 running”的最早观察时间，没有按照样本 URL 的端口、对应进程和启动实例匹配。编辑器 3000 已运行、字体服务 8080 尚未启动时，字体连接失败会被标成“服务运行之后”，实际上只证明另一个受管服务此前被观察为运行。

修复要求：只有能关联到同一目标服务/启动实例时才输出前后关系；不能关联时返回 unknown，并保留原始采样时间。不要以任意进程的 running 观察充当目标接口的启动时间。

验收要求：3000 已运行、8080 探测失败、随后 8080 启动成功。8080 首个失败不能被描述成目标字体服务启动之后的观察。

## 建议修复顺序

1. 当前事实和剩余问题：问题 1、3、5，消除失败已修复但仍被当作当前问题的输入。
2. Observer 持续事实输入：问题 2，让其能及时观察正常推进。
3. Worker 流终止保护：问题 4，阻止不完整响应进入工具执行。
4. 按上述场景补验收，再重新运行启动 PPT 项目的真实任务，检查请求上下文、重复次数和总耗时。流式接收已经存在，但不能仅凭 `stream=true` 断言总耗时下降。
