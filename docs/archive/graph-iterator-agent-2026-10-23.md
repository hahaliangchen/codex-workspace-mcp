# 图迭代式 Agent：设计对照与改造方案

日期：2026-10-23
代码基线：`da6a7cb`（任务树），加上工作区里尚未提交的“宿主顺序派发”改动（`task_frames.rs` 的 `schedule`，10:34 修改）。
依据：`task_tree_context_plan_2026-10-22.md`、`ppt-task-tree-real-e2e-2026-10-22.md`，以及当前源码。

## 1. 目标模型

用烧水热菜来说明：

```
任务：烧水热菜
  步骤：锅里加水 ✓
  步骤：放上托盘 ✓
  步骤：启动开关 ▶
      └ 任务：修锅（开开关时发现锅坏了）
            步骤：检查 → 换零件 → 试通电
      ← 返回：“锅底接触不良，已修好”
  步骤：启动开关 ▶（继续）
```

### 1.1 几条原则

1. **宿主是迭代器，AI 是无状态函数。**
   - 整张图是一个生成器，每个节点也是一个生成器。宿主负责推进、挂起和恢复。
   - AI 不记任何东西，不知道也不需要知道“挂在哪里”。每次调用都是 `f(上下文) → 动作`，上下文由宿主按图现拼。
2. **两类节点。**
   - **任务节点**：有目标，是一个上下文范围。进入时产出步骤列表，结束时向调用方返回一句结论。
   - **步骤节点**：任务下面的一个执行单元。内部可以多次调用模型、调用多个工具。承接上一步的结果，产出自己的结果交给下一步，就像中间件。
3. **临时任务就是 `yield`。** 步骤执行中遇到障碍时，产出一个任务节点挂在自己下面，自己挂起；子任务完成后宿主自动恢复这个步骤，类似 redux-saga 的 `yield call(修锅)`。
4. **上下文随结构销毁。** 子任务结束时，它内部的全部过程丢弃（原文留在历史里可查），只把返回结论交给挂起的步骤。
5. **状态只看完成与否。** 节点要么 done，要么 undone；undone 带一个原因（失败、受阻、需要用户），交给父节点决定怎么办。

### 1.2 上下文拼装规则

每次调用 AI 时，宿主从根走到当前节点，沿途拼装：

| 来源 | 给什么 |
|---|---|
| 祖先任务节点 | 目标、约束；分支任务再给插入原因 |
| 当前任务中已完成的步骤 | 每步一句结果 |
| 上一步 | 完整结果（中间件承接） |
| 当前步骤 | 自己的完整本地记录：模型回复、工具调用和结果 |
| 当前步骤下已完成的子任务 | 只给返回结论 |
| 继承材料 | 祖先挂上的设计规范、模板、技能说明（pinned） |
| 其他分支 | 不给 |

由此可以推出：一次调用的大小 ≈ 路径深度 × 每层摘要 + 当前步骤自己的记录。它不会随着做到第几页而增长。

## 2. 现状对照

### 2.1 已经做对的

`da6a7cb` 已经实现了这套模型的骨架：
- 事件驱动的任务树（`task/node_*` 事件和 `agent_task_nodes` 缓存表）；
- 节点有独立的工作帧，子节点返回时折叠并恢复父帧（`ChildReturn`）；
- 返回必须带证据，深度上限为 4；
- 用户指令可以指定作用范围（`scope_message`）；
- 回退和重启时恢复整条帧栈；
- 委派节点；
- 按任务帧加载工具组。

这些保留，不推倒重来。

### 2.2 差距

**差距一：控制流在 AI 手里，没有交给宿主。**

现在由 AI 通过 6 个控制工具自己维护栈：`plan_tasks`、`start_task`、`branch_task`、`return_task`、`split_task`、`scope_message`。10-22 真实 PPT 测试（任务 `task_78f4…`）正好暴露了这个问题：
- 模型多次 `start_task` 自己的节点（567、658、772、1286 等），全部被拒绝；
- 反复新建“制作全部 8 页”这类重叠的泛任务，最终撞上深度上限；5 次 `split_task` 全部报 `TASK_DEPTH_LIMIT`；
- 确认大纲后，宿主在根节点下建了 8 个页面节点，但一个都没被启动。163 次页面操作全部发生在同一个泛任务节点里。

正在进行的 `schedule` 改动让宿主按顺序自动启动下一个步骤，方向是对的。但 `start_task` 和 `plan_tasks` 仍然对执行中的 AI 开放，AI 依然可以自己规划、自己进入、自己嵌套。

**差距二：步骤之间传的是整份对话，不是结果。**

未提交改动里的 `child_material` 对顺序步骤是这样处理的：

```rust
let pipeline = node.executor == "inline" && node.kind == "planned";
let mut messages = if pipeline { parent.messages.clone() } ...
```

`focus_frame` 的注释写的是“step transitions never discard them”。也就是说，第 2 页继承第 1 页的全部对话，第 20 页继承前 19 页的全部对话，上下文仍然按页线性增长，最后只能靠压缩兜底。这恰恰是 10-22 凌晨 20 页测试失败的原因。中间件应该传递的是上一步的**结果**，而不是上一步的**过程**。

改动想解决的问题是“下一步不必重新读材料”。这个问题应该用继承材料（pinned）和上一步结果来解决，而不是把对话整份复制过去。

**差距三：节点不分类型，任何节点都能再规划子节点。**

现在只有一种节点（root/planned/branch 只是来源不同），每个节点都能调 `plan_tasks`。真实测试中的递归规划就是这样产生的：“制作 8 页”下面又规划出“制作与检查 8 页”。

按目标模型：
- 只有任务节点会产出步骤，而且只在进入任务时产出一次，失败后重新规划时再产出；
- 步骤节点不能规划，遇到需要拆分的情况只能 `yield` 一个子任务，并且必须写明原因。

**差距四：一个步骤跑太久时，靠压缩而不是靠拆分。**

现在的处理是 60% 时提醒拆分（`split_task`），85% 时宿主压缩。在目标模型里，步骤记录过长说明这个步骤太大。60% 时应该让 AI 把剩下的工作 `yield` 成一个子任务，压缩只作为最后兜底。这一点和现有方案一致，只是 `split_task` 的语义可以简化成 `yield`（见 3.2）。

## 3. 改造方案

### 3.1 宿主迭代器

```
run(任务节点 T):
    steps = T.steps ?? plan(T)               // 进入任务时规划一次（PPT 页面直接取已确认的大纲）
    prev = T.input
    for step in steps where step 未完成:
        loop:
            r = execute(step, assemble(step, prev))   // 一次或多次 AI 调用，直到 AI 交出结果或 yield
            if r 是 yield(子任务 S):
                ret = run(S)                          // 递归；S 的帧在返回后丢弃
                step.log.push(子任务返回(ret))          // 只把结论放回步骤记录
                continue                              // 恢复同一步骤
            if r 是 done:   prev = r.result; 丢弃 step.log; break
            if r 是 undone: return replan_or_bubble(T, step, r)
    return summarize(T)                      // 任务结论交给调用方
```

- `assemble` 只在一个地方实现，规则按 1.2。
- 挂起和恢复就是 `step.log` 存在库里。宿主随时可以从任务树和步骤记录重建状态，重启、回退都依赖这一点。
- `plan` 和 `summarize` 也是 AI 调用，但上下文很小：任务卡片加上各步骤结果。

### 3.2 AI 在不同时机能用的工具

| 调用时机 | AI 的输出 | 可用工具 |
|---|---|---|
| 进入任务（plan） | 步骤列表：标题、目标、完成条件、需要的材料和工具组 | 只读工具，加 `submit_steps` |
| 执行步骤（execute） | 用业务工具干活，最后交出结果，或者 yield 一个子任务 | 业务工具，`yield_task(title, goal, done_when, reason, inputs)`，`finish_step(status, result, facts, evidence, …)` |
| 失败后重新规划（replan） | 修改剩余步骤，或者让整个任务以 undone 返回 | 只读工具，加 `submit_steps` / `finish_task` |

执行中的 AI 不再有 `plan_tasks`、`start_task`、`split_task`：
- 进入和推进全部由宿主完成；
- 规划只在 plan 和 replan 时发生；
- `scope_message` 保留（用户插话需要定作用范围）；
- 委派仍然通过步骤的 `executor: delegate` 由宿主启动。

### 3.3 返回协议

保留现有 `return_task` 的字段和宿主校验：

| 字段 | 要求 |
|---|---|
| `status` | done / failed / blocked / needs_user |
| `result` | 结论，几句话到一段话 |
| `facts` | 事实列表，每条带证据 |
| `outputs` | 产出的资产引用 |
| `evidence` | 证据事件 |
| `open_issues` / `question` | undone 时说明原因或要问用户的问题 |

`result` 和 `facts` 是下一步拿到的“上一步结果”，所以要求写清楚**改变了什么外部状态**，比如“已把 shared.css 第 40 行改为 …”“锅换成了新的”。

### 3.4 PPT 映射

- “制作 PPT”是任务节点，它的步骤就是已确认的大纲页面，宿主直接生成，不需要再调一次 plan。
- 设计规范、模板、ppt-master 技能说明挂在这个任务上作为继承材料，每一页自动带上，不用重复读取。
- 每一页的步骤上下文是：任务目标、前几页各一句结果、上一页完整结果、本页要求、本页自己的记录。
- 本页发现模板有问题时，`yield` 一个“修模板”子任务，修好后回到本页继续。
- 整体验收（全部页面检查通过、导出）是最后一个步骤。

## 4. 迁移步骤

每一步都可以单独合入，并用现有的 20 页 HTML 夹具验证。

1. **顺序步骤改为只传结果。** 修改 `child_material` 的 pipeline 分支：不再复制父帧的 `messages`，改为装配“路径 + 已完成步骤的一句结果 + 上一步完整结果 + 继承材料”。用 20 页脚本验收核对两项：每页输入不随页序增长，共享材料的重复读取仍为 0。这是收益最大、改动最小的一步。
2. **区分节点类型。** 在 `agent_task_nodes` 中加 `role`（task / step）。旧数据中，根节点和分支节点视为 task，planned 节点视为 step。
3. **按调用时机分发工具。** 执行步骤时去掉 `plan_tasks`、`start_task` 和 `split_task`，新增 `yield_task`、`finish_step`，并把 `return_task` 重命名为 `finish_step`，旧名称保留为别名。规划只在 plan 和 replan 时进行。
4. **宿主迭代器接管推进。** 把 `schedule` 扩展为 3.1 的完整循环，包括 undone 时进入 replan、needs_user 时结束本轮并等待用户。
5. **拆分改成 yield。** 60% 软阈值时，提醒 AI 把剩余工作 `yield` 成子任务。`split_task` 退场，85% 的兜底压缩保留。
6. **用真实模型复测 PPT。** 重点看三件事：页面节点是否被逐个推进，是否还有自我启动和递归规划，每页输入是否平稳。

## 5. 需要拍板的问题

1. 步骤承接时，除了上一步的完整结果，更早的步骤是否只给一句结果？我的建议是：是。
2. 任务节点进入时规划出的步骤，是否需要用户确认？现在只有根任务定义和 PPT 大纲需要确认。我的建议是：保持现状，其余步骤由 AI 决定，在 Flow 图里实时可见，用户随时可以插话纠正。
3. 与正在进行的 `schedule` 改动如何衔接？它和第 4 步方向一致，但第 1 步（只传结果）和它的“整份传递”是相反的。需要先和那边对齐，再动 `task_frames.rs`。

### 6.2 测试

- 新增 `yielded_task_runs_its_own_steps_and_the_suspended_step_resumes_with_only_its_result`，完整走一遍烧水热菜：
  - 步骤“开开关”不能规划，只能 yield“修锅”；
  - 修锅任务规划出自己的两步，由宿主执行；
  - 开关步骤恢复后只看到“修好了”，看不到修锅过程；
  - 下一步“上菜”只看到“开关”这一步的结果。
- 新增 `steps_receive_earlier_results_but_never_earlier_transcripts`：
  - 第二步看得到第一步的结果和事实，看不到第一步的工作记录；
  - 第三步看得到第二步的完整返回，第一步只剩一句；
  - 步骤加载的工具组不会带回父任务。
- 20 页脚本验收通过：22 个节点全部完成，第 7 页修复分支挂在第 7 页下；后五页与前五页估算输入之比为 1.03，共享材料重复读取 0 次。
- 全量 `cargo test`：260 通过、0 失败、6 忽略（Linux）。

### 6.3 规划闸门与真实模型博客验收

新增规则：
- **规划闸门**：任务节点在还没有步骤时，只能读，不能改。“任务节点”指分支，或定义已确认的根节点。写文件、运行程序、浏览器操作都会返回 `PLAN_REQUIRED`，必须先 `plan_tasks`（`task_frames::ensure_planned`）。
- **根节点消息自动定范围**：在根节点收到的用户消息，作用范围只可能是根，宿主直接记为 `n0`，不再要求模型调用 `scope_message`。

验收夹具在 `tests/fixtures/blog_build`：用 Python 写一个静态博客生成器（文章页、首页、标签页、RSS、搜索索引、单元测试）。埋设的缺陷是共享的 `lib/slug.py` 会丢掉中文字符，`check_site.py` 同时校验这个共享函数本身。测试入口是 `context_acceptance::real_model_blog_build_repairs_an_unexpected_dependency`（`--ignored`，模型 gpt-6-luna）。

| 运行 | 结果 | 任务树 |
|---|---|---|
| 1（没有闸门，简单夹具） | 通过 | 只有根节点，29 次工具调用；模型在 `build.py` 里包了一层绕开缺陷，没有修共享函数 |
| 2（没有闸门，加强夹具） | 通过 | 只有根节点，24 次工具调用；修了 `lib/slug.py` |
| 3（有闸门） | 通过，169 秒 | 根节点读 SPEC → 规划 1 步“实现并验证”（19 次请求，峰值约 2.4 万 token）→ 根节点再规划 1 步“验收”（2 次请求）→ 根节点核对后返回。全程没有压缩 |

结论与遗留：
1. 宿主驱动、步骤只传结果、规划闸门，在真实模型下都按预期工作。
2. 真实模型还没有触发过 `branch_task`。原因是检查脚本会校验共享函数，模型动手前读了它，提前发现了缺陷，所以在步骤里顺手修掉了。要验证“干到一半才发现意外”，需要换一种只有运行时才暴露的缺陷。
3. 步骤会重复读根节点读过的材料（运行 3 里 `SPEC.md` 读了两次）。原因是规划时没有把它声明为输入或 pinned，可以考虑让宿主把任务已读的材料自动作为步骤输入。
4. `return_task.outputs` 填了文件路径而不是资产 ID，被拒一次（“output asset not found”）。可以考虑接受工作区文件路径。

### 6.4 运行时缺陷验收（运行 4）

夹具 `tests/fixtures/blog_runtime`：共享的 `lib/markdown_lite.py` 按正文长度做缓存。正好有两篇文章正文都是 39 个字，后一篇会拿到前一篇的渲染结果。代码和检查脚本都不点名这个函数，缺陷只会在构建后表现为“某篇正文缺失”。测试入口是 `real_model_blog_build_meets_a_runtime_only_defect`。

结果：检查通过，用时 259 秒，46 次工具调用，没有压缩。

| 节点 | 请求数 | 峰值输入 | 说明 |
|---|---|---|---|
| 根 | 10 | 约 1.7 万 | 读取后规划两步；两步都完成后核对检查结果并返回 |
| 步骤 1“检查规格与输入” | 5 | 约 1.1 万 | 只读了材料，返回一份笔记 |
| 步骤 2“实现并生成站点” | 31 | 约 3.3 万 | 第一次检查失败（事件 277）→ 改 `markdown_lite.py`（288）→ 没重新构建就检查，又失败（300）→ 排查 8 次调用 → 重新构建 → 检查通过（406） |

观察：
1. 缺陷确实在运行时才暴露，模型也定位到了共享函数并在源头修好了。但它是在当前步骤里直接修的，**没有调用 `branch_task`**。修复加排查约 11 次调用，全部留在步骤 2 的上下文里。
2. 步骤 1 是一个“只读材料”的步骤，步骤 2 又把同样的材料全部重读了一遍，步骤 1 等于白做。

### 6.7 outputs 接受工作区路径（运行 8）

`return_task.outputs` 现在接受两种写法：
- `asset-` 开头的照旧当作资产 ID 校验；
- 其他当作工作区路径，要求文件存在，并且来自本节点或已验收的子节点：要么有一次成功写入这个路径的记录，要么本节点有过一次成功的程序运行（覆盖生成出来的文件）。

运行 8 结果：通过，用时 223 秒，40 次工具调用，没有压缩。任务树为：根 → 步骤“实现并验证” → 临时任务“修复共享渲染函数” → 步骤“修复并验证”。

- 5 次 `return_task` 都用了文件路径作为 `outputs`，**全部通过**，“output asset not found”降为 0 次。
- 剩下 1 次被拒是 `UNRELATED_OR_UNSUCCESSFUL_EVIDENCE`：临时任务返回时引用了孙节点（它的步骤）里的工具事件作为证据，按规则只能引用直接子节点的返回。下一次重试时改成引用子节点的返回，就通过了。
