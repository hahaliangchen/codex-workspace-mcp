# Agent 组织者流式响应与任务交接修复计划

日期：2026-10-07

## 1. 实施目标与边界

将 Organizer 请求改为 `stream=true`，完整支持流式调度工具调用；修复任务内部汇报打断执行、Observer 事实缺失、当前成功结果丢失和旧回执驱动重复上传的问题。

保持用户已经确定的架构：

- Organizer 与 Worker 使用同一模型、供应商及用户选定的推理配置，区别在上下文。
- 一个 Flow 节点是一件具体任务；节点内部可以有多轮模型调用。
- Worker 接收当前任务输入，执行并检查，返回实际结果；Organizer 根据上一步返回决定下一步。
- 调度器负责调用、状态保存及下一节点激活。Flow 随实际任务逐步生成。
- 状态继续使用现有 `ready / running / done`，废弃沿用已有标记；不用扩展一套复杂的生命周期。
- `done` 表示任务调用已返回。负面结果、能力不可用也可返回，不等于整个用户目标已实现。
- Observer 观察同一份任务状态与执行事实，异步提供建议；不成为额外审批环节。
- 旧下游在 Flow 中保留为灰色废弃节点，可追溯其目的、结果和废弃原因。

本文件是交给实现 AI 的要求文档。本次编写未修改运行代码；实现者应将以下相关改动整体提交，尤其不能只改 `stream` 布尔值而继续按完整 JSON 解析 SSE。

## 3. 第一阶段：Organizer 改为真正流式调用

### 3.1 请求与解析一起修改

主要位置：`src/work_organizer.rs::decide`，当前请求 `stream=false`，随后 `response.bytes()` + `serde_json::from_slice` 读取完整 Chat Completion。

要求：

1. 请求发送 `stream=true`，使用 `response.bytes_stream()` 消费增量。
2. 增量拼接 `choices[0].delta.tool_calls`，按 tool-call index 分组，组装 ID、函数名及 arguments。
3. 正确处理网络块拆开 SSE 行、CRLF、UTF-8 中文跨块、事件分隔、注释/keepalive、usage 尾帧及 `[DONE]`。UTF-8 数据未完整前保持字节缓冲，不能逐网络块 lossy 解码破坏工具参数。
4. 流完成并满足明确终止条件后，得到完整 assistant message，再沿用现有 `normalize_decision` 和工具契约校验。
5. 保留“一次组织者调用只提交一个调度方法”。流中的半截参数、即便临时可解析的 JSON，也不能触发调度或修改 Flow。
6. 不完整 EOF、断流、上游错误、非法参数、多个方法均返回明确错误，并保留已有节点结果。用 `finish_reason` 与 `[DONE]` 判断提供方是否正常终止；不能把传输突然结束当作成功。
7. 供应商实际返回完整 JSON 时可兼容解析，记录 `response_format=json`，不要伪造 SSE 增量或首增量时间；正常 SSE 为默认路径。
8. 保留现有参数大小限制，对接收缓冲也设置合理上限。只做本次请求内的缓冲，不增加永久原始响应堆积。

### 3.2 复用 Worker 的解析经验，分开输出通道

已有参考：`src/agent_service.rs::consume_model_stream` 与 `src/work_executor.rs`。

该解析函数会直接发 `assistant/delta`，因此不能直接用于 Organizer 后把内部调度文本混入 Worker 的用户答复。可提取纯 SSE/tool-call 累加器，分别接 Worker 和 Organizer 的事件回调；也可先实现独立 Organizer 消费器，共享纯解析逻辑。

接口应返回完整 message 与统计信息。Organizer 的执行方法仍由宿主在流完成、验证通过后调用一次。

### 3.3 进度、取消与时间统计

沿用 `organizer/request_metrics`、请求上下文调试及现有任务取消机制，补充：

- `response_headers_ms`：收到 HTTP 响应头。
- `first_chunk_ms`：收到首个响应块，可能仅为心跳。
- `first_delta_ms`：收到首个有效模型增量。
- `first_tool_delta_ms`：收到首个工具调用增量。
- `response_complete_ms`：响应完成。
- `response_format`、`finish_reason`、`received_done`、usage、接收字节数与最终结果。

全部时间相对同一次请求开始计算；缺失为 null，不能用 0 代替未收到。

在发请求、读流及取消路径上及时响应现有 CancellationToken。保留现有整体超时；心跳不能无限延长总时限。超时/取消也要结束对应请求上下文，保存部分计时，不能留下永久 pending 记录。

前端可利用节流后的 Organizer 进度事件显示“等待响应 / 正在接收决策 / 决策已完成”和耗时。调试模式展示时间及增量统计。避免每个 token 引发整张 Flow 重绘。

**流式改造的可验收收益是更早获得进度、能定位首增量与生成耗时、取消更及时。总响应时间是否下降用实际计时比较，不能承诺把 174 秒直接变成几秒。** 本阶段保持用户模型与推理配置，便于比较。

## 4. 第二阶段：修复 Worker 汇报与 TaskReturn 边界

主要位置：`src/work_scheduler.rs::finish_round`、`src/work_executor.rs`、`src/agent_service.rs`。

当前 `idle_rounds >= 1` 将一次只有 `report_progress` 的模型轮次变成 Organizer 交接。

要求：

1. `report_progress` 更新当前节点的目的、已知事实与进度后，下一模型轮继续当前 Worker 任务；不改变节点，不生成 TaskReturn，不单独调用 Organizer。
2. 不要求 Worker 每个小工具调用前都用一轮模型先汇报；允许同轮汇报与实际操作。
3. 主要交接边界是明确 `yield_work`/有效 TaskReturn、宿主完成检查返回、真实阻塞、拆分/回溯请求以及有界的持续停滞。
4. 沿用已有停滞计数，但判断实际新增信息/操作，区分正常一次汇报与持续只承诺不行动。反复重写报告不得重置真实停滞；处置也不能无限重派同义任务。
5. 普通知识问答可以直接返回答案并完成一个节点，不要求文件操作或工具调用来证明“在工作”。
6. 返回不达预期结果后，仍封存该次调用。下一步由 Organizer 根据结果安排修复、补充检查或给用户说明限制。

## 5. 第三阶段：让 A 的返回真正传给 B

主要位置：`src/work_scheduler.rs::apply_inner / enqueue / organizer_input / compact_current_result`，相关 Flow 适配。

### 5.1 调度顺序

正常串联：

```text
A 执行 → A 返回 → 宿主保存 A 的结果 → Organizer 决定 B
       → 校验 B 的输入引用 A 的有效返回 → 激活 B
```

目前“调度新任务”会先废弃尚未完成的当前节点，再解析新任务依赖，导致正确引用当前生产者也被拒绝。

要求：

- 正常交接先封存生产者返回，再校验后继输入；完成 A 后创建 B 不得废弃 A。
- 当前任务仅汇报、没有返回时，继续当前任务；不能因为一次普通调度自动假装其交付成功。
- 如确需取消、拆分或回溯，明确该操作及原因，保存已有阶段事实，按照既有规则废弃相应下游。
- 不允许在没有返回的情况下自动编造输出或给未完成任务盖完成章。
- 调度验证保持事务性，失败不得留下部分废弃、队列变更或 Flow 节点。
- 错误提示区分：任务尚未返回、任务已废弃、revision 不匹配、字段未导出、引用类型错误。不要都报笼统的 `has no active frame in plan`。
- 模型使用正常小接口，不再让它构建整个 Flow 或手工管理 IDs。

### 5.2 完整、简短且按发生顺序的路径

Organizer 输入依次提供：最新用户目标、上一步实际返回、简短执行路线、当前有效事实/资源、剩余条件、相关建议。

**Flow 节点本身就是组织过程描述的来源。** 宿主根据节点已保存的目的、实际动作、返回和执行顺序，生成“第一步做了什么，第二步改变了什么，当前已经做到哪一步”的简短文本。画布与 Organizer 使用同一份节点结果，避免另维护一套可能不同步的过程总结。

这项文本投影是本次改造的核心交付，不能只增加节点颜色、状态枚举或让模型读取一堆 ID 自行拼接历史。可沿用 JSON 传递结构化返回，但输入同时要有清楚的按序过程描述与最新状态结论。

路径每项只保留理解路线所需字段：执行顺序、节点 ID/执行 revision、任务目的、实际结果、时间/来源、必要限制、历史或废弃标记。代码与详细工具日志继续存记事本，按需读取。

要求：

- 路线按实际执行/返回顺序组织，回溯时明确第几次执行；不能只按节点创建顺序推断先后。
- 废弃节点以历史摘要保留在路线中，不作为 B 的有效依赖；Flow 同步显示灰色。
- 上一步实际返回优先展示。自动检查的 summary 应说“两个接口返回 200，服务已启动”，不能只重复“已完成启动并检查的条件”。
- 同一事实不需要把所有原始返回重复注入；上一步返回与路线摘要各有用途，避免同时塞几份完整结果。
- 旧负面观测保留其采样时间，当前事实明确指向后续成功观测。变化的状态由宿主事件更新，不要求模型额外做一轮历史协调。
- 将“下一步准备做什么”的目的汇报与“已经完成什么”的节点返回区分。未执行的承诺不能写入路线的完成结果。
- 对同一对象/属性，按真实执行事件顺序表达状态变化；已确认的新结果更新当前事实，旧结果保留为“当时的历史观察”。来源不同、对象不同或新记录仍是猜测时不能盲目覆盖，明确未确认之处。
- 动态资源的最新样本过期时，标明“当前未知、上次成功为某时”，不能退回更早的失败当作当前状态。
- 过程描述根据现有结构化事实与节点返回生成，正常情况下不用额外调用模型做一轮总结。保留结果引用便于有具体疑问时读取详细材料。

示例表达，字段可沿用已有结构，不要求照抄新类型：

```text
第 1 步：检查服务；结果：连接拒绝（当时的观察）。
第 2 步：启动服务；结果：受管进程启动，两个接口 HTTP 200。
第 3 步：上传文稿；结果：目标文件关联加载成功，共 8 页。
第 4 步：字体/截图检查；结果：字体请求记录不可得；截图已生成，模型看图不可用。
最新已知事实：文稿已加载。剩余限制：字体使用情况、视觉检查未确认。
```

“未知、工具无法观察”不能自动翻译成“上游没做”，重新上传也不能解决模型无法看图。

### 5.3 “先失败、后成功”的明确表达与验收

用户类比：“前几天生病，昨天已好了”。正确过程描述应同时保留历史与变化：前几天生病是历史事实，昨天已恢复是最新已确认结果；不能把它们作为两条无时间关系的“当前结论”并列注入。

对本项目的实际表达：

```text
第 1 步：探测字体服务，连接被拒绝。这是启动前的历史结果。
第 2 步：启动字体服务，随后探测返回 HTTP 200，更新了第 1 步的服务状态。
第 3 步：上传 PPTX，目标文稿已加载，共 8 页。
当前已知：服务启动后曾返回 200；文稿最近确认已加载。
剩余问题：浏览器实际字体请求记录未取得，模型无法查看截图。
```

验收时直接检查 Organizer 的实际请求文本：必须能读出完整的失败→修复→成功→剩余限制关系；旧失败不能出现在未标注时间/历史身份的当前结论中。后续因该旧失败再次启动或上传，应判为未通过，并检查文本投影、当前事实及模型决策各层，不能只把节点再改名。

## 6. 第四阶段：统一当前事实，修复 Observer 投影和浏览器回执

### 6.1 Observer 输入

主要位置：`src/observer_service.rs::pack / observation`，`src/agent_service.rs` 的 observation 创建点。

要求：

- 每轮目的、动作结果和任务返回先写入当前节点状态/事件。Observer 能读取该节点的最新版本与顺序，而非只看派单标题和结束摘要。
- 异步模型分析可按有意义的变化合并观察，不要求每个 token 都调用 Observer；事件接收与事实保存持续进行。
- 明确保留任务目标、已执行动作、返回结果、关键事实值、时间/来源及限制。
- `exported_fields` 只是一份目录，不能当作实际交付。HTTP 结果包含 URL/status/error/sample time；进程结果包含 ID/running/归属；浏览器结果包含页面与关联上传信息。
- 去掉按对象前 N 个键截断事实的做法，改为按业务字段选择摘要，必要时返回材料引用。
- 观察意见携带对应节点、执行 revision 和观察事件版本。旧建议保留为历史，避免晚到的“缺状态码”推翻后续已记录的 200。
- 上下文材料不足时读取已有结果或表达“当前输入缺材料”，不直接建议 Worker 重做动作。
- Observer 继续辅助，不创建独立确认/审批轮，正常 TaskReturn 不必等待其模型答复才能推进。

### 6.2 当前浏览器事实与历史回执

主要位置：`src/work_scheduler.rs` 的浏览器回执/availability，`src/browser_control.rs::validate_upload_receipt`。

要求：

- 当前受控 session/page/upload attempt/load state 由宿主工具结果维护，是资源事实；生产任务的历史/废弃标记不应等价为当前页面丢失。
- 原上传交付仍归属于原节点，禁止将废弃交付重新伪装成合法依赖。当前资源状态作为宿主事实独立展示，并明确来源。
- `browser_upload_availability` 区分“哪个历史回执过期”与“当前页面有哪些有效状态”；旧回执 `browser_session_changed` 不得代表所有当前上传均失效。
- 同一会话的后续 `browser_read` 若明确关联当前上传、loaded 和页码，应进入 Organizer 当前事实，不可只留下自由文本声明。
- `browser_document_path` 表示 PPTX 文件路径；页面 URL 使用页面事实字段。对把编辑器 URL 填入文档路径的声明给出清晰纠错。
- 修改 Organizer 提示词中“回执 unavailable 就重新上传”的无条件规则：先结合当前资源和最新返回判断；仅确认当前文稿确实缺失、文件不符，或旧会话关闭且无当前文稿时，安排重新打开/上传。
- 采样过期但仍需当前状态时，优先只读当前页面检查；保留上传成功历史，按结果再决定后续。

## 7. 第五阶段：补齐导致重复工作的工具能力

### 7.1 HTTP 观察

- 返回最新样本、可复用性、年龄与失效原因；结合服务启动事件明确观测发生在启动前/后。
- 新鲜结果满足问题时复用；宿主已确认旧样本失效且当前任务允许采样时，合法获取新样本无需先失败一遍才补原因。
- 需要额外新样本时保留原因要求，但避免将已过期观察与无意义重复探测统一处理。
- `http_status=null` 仍明确表示未收到 HTTP 响应。

### 7.2 字体与正常网络请求

- `browser_diagnostics` 当前过滤正常 `/api/fonts` JSON 200，fetch/XHR 也只记录错误。补充有界的正常请求记录，可按 URL/类别读取 URL、method、status、时间及失败类型。
- 可以利用原生 CDP Network 事件；记录有来源/覆盖范围，明确缓存、跨来源不可见或工具没有捕获的状态。
- 服务端 API 200 与浏览器实际请求成功是不同事实，分别返回。
- 空记录明确解释“观察范围内无记录”，不宣称“没有请求”或“字体已成功加载”。重复读取不会扩大工具覆盖范围，应让 Worker/Organizer知道这项限制。

### 7.3 图像与页面操作

- 图像 capability 未知且无备用模型时，明确当前图像输入不可用；截图仍可生成并交付用户，模型不能声称已看图。
- 收到 unavailable 返回后，组织者依据限制收尾或使用已存在的可行能力，不反复分派相同视觉任务。保持 Organizer 与 Worker 同模型，不静默换模型或推理配置。
- 网络/诊断任务不要设置 `visual_goal`。
- 控件读取与点击的文本/accessible label 匹配规则一致；已有精确 selector 时优先使用。
- 有界重复点击可在一次模型响应中调用现有工具数次，再读取结果；必要时提供小范围的批量操作工具。每个可确定的小点击无需单独经历组织者决策。

## 8. 实施顺序与交付

建议分提交推进：

1. **流式组织者与计时**：`stream=true`、SSE 拼接、完整工具决策提交、取消/超时、独立进度事件与调试展示。
2. **任务返回与串联交接**：纯汇报继续 Worker、上一步返回后再派单、依赖校验事务、按序的实际结果摘要。
3. **事实共享与回执**：Observer 完整输入、当前资源状态与旧历史分清、消除无条件重传提示。
4. **工具能力与真实场景验收**：HTTP 复用、正常字体 API 请求记录、图像不可用返回、浏览器小动作往返。

所有修改遵守现有权限、取消机制、材料记事本和 Flow 事件兼容性。提交说明用中文，说明修改、验收结果和剩余限制。实现期间如有运行中的 Agent，先完成可审查改动；切换宿主版本安排在试验任务结束后。

## 9. 验收要求

实现 AI 应补充针对性验证并记录结果，不仅检查编译。

### 协议与交接场景

| 场景 | 必须结果 |
| --- | --- |
| 工具 arguments 分多帧，中文跨网络块 | 拼接正确，完成后只调度一次 |
| 半截 JSON、断流、错误帧、多个方法 | 明确失败，调度器/Flow 无部分写入 |
| 正常流结束、usage 尾帧、兼容 JSON | 正确方法、真实格式与时间、请求记录结束 |
| 取消/超时发生在等响应或读流时 | 及时退出，保存部分统计，无后继任务执行 |
| Worker 一轮只汇报下一步 | 当前节点继续，Organizer 调用次数不增加 |
| Worker 持续只汇报、没有新增信息/操作 | 有界停滞处置，不能无限重派同义任务 |
| A 返回，B 依赖 A 的输出 | A 保持 done，B 获得准确字段与 revision |
| 新任务声明不合法 | 保留当前节点、既有结果和队列 |
| A 返回连接拒绝，B 启动并返回 200 | 历史路线保留拒绝，当前事实使用后续成功观测 |
| Observer 检查启动返回 | 能看到实际 200、时间、进程结果，不催重新检查 |
| 旧 Observer 意见晚到 | 关联旧版本，不覆盖当前事实 |
| 上传成功后换到检查节点 | 当前 session/文稿状态保留，无需重新上传 |
| 旧会话回执失效但当前文稿 loaded | 旧回执为历史，当前成功不丢失 |
| 回溯修复上游 | 旧下游灰色保留，下一步引用新返回 |
| 字体 API 正常 200 请求 | 浏览器工具能在已声明覆盖范围内返回该请求 |
| 模型无法看图 | 返回截图和明确限制，结束调用，不反复重派 |
| 简单知识回答 | 一个节点可直接回答并返回，无工具操作要求 |

### 真实 PPT 启动任务

沿用试运行中的真实任务与模型配置，打开上下文调试，逐节点核对：

1. 服务观察返回实际状态。
2. 服务不足才启动；启动结果直接给下一步，不单独再建同义服务确认任务。
3. 真实文件上传并确认关联加载结果；同一当前文稿正常时只上传一次。
4. 字体/浏览器检查获得请求记录，或明确报告工具覆盖限制。
5. 截图及可用的视觉查看；不可看图则返回限制。
6. Organizer 根据最后返回 `finish_request`，如存在未验证项使用 `achieved=false` 和具体 unresolved，而非重置上传任务。

最终记录：墙钟时间、三角色请求次数、工具调用、纯汇报轮、重复原因、依赖错误、各请求首增量/完成耗时，以及浏览器保留状态。页面切换后读取、状态真正变化后的重探测可有必要；验收重点是每次操作有新的需要，且旧结果正确进入下一步。

验收目标：消除本次复现的“汇报就交接、成功回执消失、旧失败驱动重做、不可看图仍循环”路径；流式可观察并可靠提交完整决策。用这些实际结果判断完成，不以新增了多少状态或 Flow 字段作为成果。
