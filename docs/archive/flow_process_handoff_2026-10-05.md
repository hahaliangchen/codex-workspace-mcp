# Flow 与项目启动流程修复交接

## 用户要求

每次用户请求都是 Flow 的总目标。组织者把总目标逐步分解为具体任务节点，决定先做什么、接下来做什么；程序调度器执行依赖顺序和状态同步，Worker 只处理当前节点的目标与最小上下文。

例如“启动现有应用并打开项目自带示例 PPT”应有以下结构：

```text
启动应用并打开示例 PPT（总目标）
├─ 确认启动入口、必要条件和示例入口（未知时才调查）
├─ 启动应用并确认实际页面就绪
└─ 在应用中加载示例，确认出现幻灯片
```

父子关系表达目标分解；上游依赖表达先后顺序及产出传递。组织者可以先分配一个子任务，取得结果后再决定后续子任务，不需要一次猜完所有步骤。已经明确的条件直接作为输入，避免专门创建重复调查任务。

简单“解释某技术点”可以直接以总目标节点完成回答。复合目标需要具体子任务，不能因为涉及文件少、任务描述短，就把所有动作塞入一个 `output` 工作包。节点按具体工作目标划分；一个节点内可有多轮实现、检查、修复，出现新的独立问题再拆分。

完成叶子节点后封存结果，仅将必要产出传给后续节点。父节点需等待相关子节点完成，或明确记录尚未完成的部分，不能把启动成功等同于示例已经打开。

## 1. 总目标没有拆成具体节点

### 现象与原因

旧组织者把“启动应用并打开示例 PPT”安排为一个 `node_id=direct`、`completion=output` 的工作包，目标同时混合调查、进程启动、页面验证、浏览器操作以及阻碍汇报。Worker 在同一个节点长期调查。

新代码会为每个工作包自动画节点，并为直接工作包生成 `work_<order_id>` 节点 ID。只画出这个大工作包仍然不能满足用户需要的父子任务结构。`TaskTree`、`flow_update`、`parent_id` 与依赖工作队列已有基础，但选择递归组织仍是可选的。

### 需要完成

- 总目标与当前执行工作包分开表达；复合请求的总目标是父节点，具体工作包绑定子节点。
- 组织者按实际目标与依赖分解，简单回答允许直接使用总目标节点。
- 先完成一个子任务，再根据其返回决定下一任务，支持动态添加下游或更小子问题。
- Worker 上下文只含当前子任务、必要约束、最新材料和指定上游产出；父节点提供目标边界。
- 已完成子节点不得被 `continue` 或普通 Observer 建议重新打开；调度器只消费其已封存返回。
- 沿用简单的 ready/running/done 工作状态，不为普通编译错误增加复杂生命周期。

### 主要文件

`src/work_organizer.rs`、`prompts/organizer_system.md`、`src/work_scheduler.rs`、`src/flow_tree.rs`、`src/agent_service.rs`、`frontend/src/model.ts`、`frontend/src/components/FlowView.tsx`。

## 2. 停滞审查与 continue 输入丢失

### 已确认的原因

旧 `finish_round` 在 `rounds_without_change >= 12` 后每轮都重新触发组织者。组织者的 `continue` 又只调用 `continue_current()`，没有应用新的 `orders`、约束、材料、结论选择或收尾标记，也没有向 Worker 传递决策 reason。

例如第 19 步组织者要求避开旧端口，实际 Worker 请求 317 中未包含此决策；第 16 步的 `final_answer=true` 也未同步。

### 已做的源码修复

- `reviewed_without_change` 记录已审查的位置，避免同一个 12 轮阈值在每轮触发。
- `continue_decision()` 合并当前工作包输入，沿用不可随意更换的目标与完成条件，保留真实操作与检查记录。
- `organizer_handoff` 将最新组织者决策交给 Worker。
- 更新材料/结论输入后重新应用当前工作包选择；修复继续执行时当前工作 ID 的恢复。

### 尚需完成

- 编译、加载新版本后复现并检查最终请求体，确认约束、材料、结论与 final_answer 真正抵达 Worker。
- 组织者不断 `continue` 而没有新信息/实际进展时仍需有界收敛；本次改动只是避免同一阈值每轮重复触发，并不证明长期空转已根治。
- 每次有具体工作产出后，调度下一子任务；无条件重复恢复同一总目标不应作为推进方式。

## 3. 端口连通与项目就绪混淆

### 已确认的原因

旧 Worker 用 `Start-Process npm.cmd` 启动，然后 `Test-NetConnection` 检查 3000/3001。父 shell 退出码为 0 和端口可连接，都不能证明目标应用成功。

第 15 步结果显示：127.0.0.1:3000 和 3001 属于 PID 25604 的 workspace MCP；Rspack 是另一个进程及监听地址。Worker 反复请求宿主地址，得到 404，并混用“进程在运行”和“应用已启动”的结论。后台启动也没有收集 npm/WASM/Rust/Rspack 的输出日志。

### 已做的源码修复

`src/project_process.rs` 已增加四个工具：`install_dependencies`、`run_project_script`、`get_project_process`、`stop_project_process`，接入 MCP、Agent 工具目录、权限与调度器。

支持直接调用 Node/npm、日志、后台进程去重、退出码、超时、取消、Windows Job Object 子进程管理。提供就绪地址时先检查端口占用。后台脚本检查要求 `running=true && ready=true`，只创建进程不会产生成功检查记录。

### 尚有缺口

目前 `ready=true` 来自受管理父进程仍运行，加指定 HTTP 地址返回 2xx，或 TCP 端口可连接。**没有把监听端点的进程归属与受管理进程组绑定，也没有核对响应是否属于目标应用。** 后补就绪地址时尤其不能仅凭已有端口可连接就认定成功。Node/npm 父进程活着也不能证明并行启动的所有组件健康。

### 需要完成

- 对目标监听端点核对进程归属，包括 npm 启动的子进程、IPv4/IPv6 地址；属于宿主/其他项目时明确返回冲突。
- 页面就绪与进程运行分别表示；前端入口及必要资源/WASM 加载异常需返回具体结果，不能被任意 2xx 掩盖。
- 多组件启动按实际所需组件判定，不能仅检查 concurrently 父进程。
- 已占用端口应定向选择项目可支持的空闲端口，或报告明确阻碍；避免重复探测旧地址，避免停止无关宿主进程。
- 端口参数要符合实际 package.json 脚本，不能假设传给并行总脚本就会到达 Rspack。
- 使用当前 PPT 项目实际启动入口做回归，记录日志、归属和实际页面结果。

## 4. 缺少浏览器交互工具

### 当前状态

项目自己的 Agent **尚未实现浏览器交互工具**。本聊天中的 Codex 浏览器能力不会自动出现在该 Agent 的工具目录。

旧 Worker 搜索 Playwright/Puppeteer 是否安装、浏览器调试端口、Chrome 进程，并尝试打开 URL。这些操作不能证明已点击示例按钮、上传文件或看到幻灯片。

源码修复目前只增加组织者的 `available_tools` 清单，以及提示词中的能力边界；能够如实报告不支持的剩余步骤，尚不能实际完成浏览器交互。

### 需要完成

- 给项目 Agent 接入独立的浏览器控制适配器，以结构化工具提供打开页面、读取页面状态、点击、上传/加载工作区文件及必要截图。
- 应用内“打开示例”作为独立叶子节点；等待页面状态表明文稿已载入、出现幻灯片或明确报错，再产出结果。
- 没有浏览器控制时，返回已确认可用的地址、示例文件和剩余人工操作，不能把任务整体标为完成，也不继续枚举自动化包。
- 保持 Worker 自己能执行节点，Observer 负责全局关注、建议和经验记忆，不能变成浏览器操作或完成判定的替代者。

## 交接建议顺序与验收

1. 先修正总目标与子任务的组织、输入同步和完成返回。
2. 完善端点归属、组件就绪和真实应用响应检查。
3. 接入浏览器交互工具，完成示例加载节点。
4. 经明确授权后加载新版本并实际回归：简单技术问答显示一个节点且不无故查代码；启动并打开示例形成父子节点，各叶子独立完成；端口冲突不会产生虚假启动成功；浏览器失败保持相关节点未完成并交付真实部分结果；同一停滞事件不会造成持续组织者往返。
