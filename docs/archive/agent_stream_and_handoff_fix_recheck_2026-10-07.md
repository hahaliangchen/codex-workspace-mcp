## 仍需修复

### 1. [P1] 成功样本过期后，旧故障会重新成为剩余问题

位置：`src/work_scheduler.rs:2233–2236、2439–2446`。

`later_http_recovery` 要求后续成功样本满足 `http_sample_freshness`。因此 A 以 blocked 返回连接失败，B 同 URL 返回 200，之后仅经过复用窗口，A 的恢复关系就消失。旧限制重新进入 `Remaining limitations`；与此同时最新 HTTP 事实仍写“当前未知，上次成功为 200”。

时间经过、其他文件修改或进程事件也可能使该成功样本不再 fresh。它们意味着不能用旧样本证明现在正常，不能撤销“B 当时已解决 A”的历史关系。

要求：将“历史故障已在 B 被解决”和“当前样本可复用”分开。过期后可新增当前状态需要刷新这一项，不能复活 A 的旧故障。后续确实再次失败时，记录新的失败及时间。

验收：blocked 连接失败 → 同 URL 200 → 成功样本过期，历史仍展示恢复；当前为未知/上次成功；旧连接失败不重回当前剩余问题。

### 2. [P1] 旧限制是否消除仍取决于自由文本中有没有完整 URL

位置：`src/work_scheduler.rs:2226–2230、2438–2441`。

对有 limitations 的任务，消除限制使用 `later_http_recovery(frame, Some(item))`，要求原句包含完整样本 URL。A 的限制写“字体服务连接失败”，即使 A 的 HTTP 样本、声明 check 都明确指向 8080，B 对同 URL 已返回 200，该限制也无法被消除。对 blocked 返回，它仍进入剩余问题。

步骤正文可以通过声明 checks 找到恢复结果，结果便出现“后续已解决匹配的 HTTP 条件”和“剩余：字体服务连接失败”并列。

要求：已可确认的资源/检查关联由结构化事实提供。不能要求 Worker 在每条自然语言限制里重复完整 URL。不能明确关联的文本保留为该步骤当时的报告，避免直接宣告它仍未解决；混合任务也不能因一个接口恢复就删除其他真正限制。

验收：A 的 blocked 限制不含 URL，A/B 的结构化样本关联同 URL，B 成功后不会继续将 A 的旧失败当作待办。

### 3. [P2] 普通任务返回的实际限制被排除出剩余问题

位置：`src/work_scheduler.rs:2434–2441、2021–2028`。

当前只有 explicit_blocker 或 visual_unavailable 才把 limitations 加入剩余问题。正常 output 返回默认 outcome=completed。Worker 返回“字体 API 请求记录未捕获”的 limitations，但没有 blocked/visual_goal 时，这项仍未完成的目标检查被排除出汇总。

该限制尚存在历史步骤和原始返回中，没有完全删除；问题是汇总不能可靠反映当前剩余工作，尤其较早步骤退出简短路径后。

要求：不要用 outcome=completed 推断 limitations 都只是历史。done 表示调用返回。对仍未确认的用户目标应保留其限制；不确定是否仍有效时明确标记待协调者判定。已恢复故障与真正未解决事项需要区分。

验收：字体诊断以普通 output 返回，limitations 明确未取得实际字体请求记录，且没有后续解决结果；剩余问题仍列该检查限制。

### 4. [P2] 同一端口重启后仍沿用旧进程的最早 ready 时间

位置：`src/work_scheduler.rs:2212–2218`。

当前匹配主机/端口后跨所有帧取 min，没有按 host_instance_id、process_id、started_at 区分启动实例。旧进程 P1 在 8080 已就绪，后来停止；P2 启动前的一次连接失败，会被关联到 P1 的早期时间，描述为匹配服务实例 ready 之后。

不同端口互相污染的原问题已解决，但无法证明这是当前或对应采样时的同一个实例。

要求：在能确认实例归属时，使用关联进程/宿主和对应实例的时间；无法确认时返回未知并保留样本时间，不输出精确实例前后关系。

验收：P1 ready → P1 停止 → 8080 连接失败 → P2 ready。中间失败不能用 P1 的 ready 时间标成 P2 启动后的失败。
