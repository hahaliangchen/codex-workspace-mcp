# 通用任务面板与 PPT 工作流实现记录

## 架构边界

任务定义属于 Agent，不属于 PPT 插件。`main_task_anchor` 保存有来源、带版本的目标、约束和完成条件；`update_task_definition` 是显式更新动作，不自动收录每条真人消息。历史原文继续存在，可以按事件引用回查。

任务定义、计划提案和确认记录写入 Agent 事件库，分别为 `task/definition`、`task/plan`、`task/plan_confirmed`。它们在构造模型请求时读取，不放进会被压缩的 Window。执行状态读取真实任务状态，结束一轮对话不代表交付完成。

任务定义是模型从真实用户要求中提炼、通过显式工具保存的内容；宿主校验用户来源、字段、大小和更新版本，不以关键词判断用户意图。模型仍须遵守最新用户暂停、恢复或变更指令。暂停不会改写任务目标。

压缩器整理当前步骤需要的材料、未解决问题、证据引用与下一步；不能更新任务定义。已建立任务定义后，旧对话不再作为所有压缩请求的强制全文输入。无新增真人消息时使用明确标注的宿主压缩请求，避免依赖窗口里是否还有真人消息。

## PPT 适配

`ppt_plan` 消费通用任务板。`commit_design_spec` 接收完整 `pages[]`，宿主从相同条目生成保存的大纲 Markdown，防止确认卡片和保存内容不同。大纲项包括稳定 ID、标题、具体内容要求和可选视觉意图；不规定坐标或固定填充槽位。

经认证的 PPT 用户接口确认具体计划版本。确认前会核对后端保存内容；正文页面修改在宿主处受到确认检查。计划变化会使旧确认失效。PPT 保存操作不再用当前稿件页数覆盖已规划的目标页数。

页面工具返回的真实页面身份和成功编辑回执记录到 `agent_ppt_page_map`。复制页面只创建容器，不标记内容完成。已有视觉分析结果按实际页面、整稿版本/哈希和计划身份判断是否有效。正式 AI 导出前要求全部计划页当前验收通过，用户主动下载草稿走独立路径。

内容继续持久化为 PPTX；JSON 仍为转换模型，HTML 为 AI 设计视图。任务、大纲和验收记录是业务状态，不是第二份长期设计 JSON。

## 显式任务确认修订

- 模型工具 `update_task_definition` 现在只写 `task/definition_proposed`。来源消息仅作追溯，不构成生效授权；普通聊天不能直接覆盖目标。
- Agent 界面通过 `POST /agent/tasks/{id}/definition/decision` 提交提案版本和布尔决定；PPT 通过带登录身份的 `decide_definition` 入口调用同一个通用状态机。通用入口拒绝插件会话，插件入口核验会话归属。
- 确认操作在同一个 SQLite 事务中校验最新提案及其基准版本，追加 `task/definition` 与 `task/definition_decided`。拒绝只记录决定。重复确认幂等，过期或相反决定拒绝，不接受替换目标文本。
- Agent 与 PPT 均显示当前任务和待确认提案、任务约束与完成条件。只有明确点击确认后才续跑；普通继续消息不调用任务确认接口。
- 大纲按钮调用 `confirm_outline(version)`，仅锁定现有大纲。未确认的任务提案不使原大纲失效；真正生效的任务内容变化使旧大纲失效。恢复完全相同的已确认任务内容可继续沿用对应大纲。
- 模型没有任务或大纲确认工具。上下文固定注入生效任务和独立标识的待确认提案；进度仍来自项目与验收记录。
