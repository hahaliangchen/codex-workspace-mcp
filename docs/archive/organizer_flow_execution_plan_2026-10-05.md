# 组织者、Flow 与单节点执行：实现交接计划

## 1. 目标与用户要求

工作区：`D:\enterpriseProject\codex-workspace-mcp`。

用户要求：组织者把用户需求安排为 A → B → C → D，向 Worker 派发能够直接执行的小任务。Worker 专注当前任务的输入和输出；组织者接收结果后决定下一步。正常执行 B 时只消费 A 的交付，不重新关注 A 的过程。发现上游交付有问题时，执行指针回到指定节点，该节点之后的旧任务全部作废；组织者从回溯节点开始重新布置任务，不恢复旧下游队列。

组织者是调度决策的核心，与 Worker 使用相同模型和配置，拥有独立上下文，不增加用户可配置的角色。程序负责验证决策、维护指针、切换上下文、记录事实和持久化。Observer 持续观察流程状态，提供建议和历史知识；它不直接移动指针，也不作为 Worker 执行的审批环节。

本文件只安排实现工作，未修改执行代码、重启服务或运行回归。实现者须先核对最新工作区，复用已有改动，避免覆盖其他工作的修改。

## 2. 要实现的运行机制

```text
用户总目标
    ↓
组织者：决定当前可执行任务及必要输入
    ↓
程序：校验并激活节点 A
    ↓
Worker(A)：实现 → 检查 → 必要修复 → 检查
    ↓
程序：记录事实，封存 A 的输出
    ↓
组织者：消费 A 的输出，决定 B / 拆分 / 回溯 / 结束
    ↓
程序：切换到 B 的独立上下文
```

组织者可以先给出 A、B、C 的计划，但只有当前节点激活。A 完成后必须让组织者接收结果并确认下一步；未执行的计划允许随新情况调整，不直接用旧队列自动执行到底。

组织者无需在每次工具调用后介入。Worker 在同一任务内自主完成多轮实现、检查和普通错误修复；交接发生在完成、明确阻碍、需要拆分、发现上游错误或停滞事件时。

简单知识回答可以只有一个节点，直接返回答案；已知材料足够的小修改也可以只有一个执行节点，不强制调查、规划、Coding、Verify 四段流程。

### 2.1 程序分层：组织者 → 调度器 → 执行器 → Worker

用户进一步明确的职责映射：

| 组件 | 职责 | 持有的视野 |
| --- | --- | --- |
| Organizer（组织者，AI） | 把需求转为任务，解释交付，决定创建、选择、调整、回溯哪个任务 | 总目标、任务关系、各任务的浓缩交付及相关阻碍 |
| Scheduler（调度器，程序） | 校验并落实组织者决策；创建任务进程，维护就绪任务与当前指针，驱动执行器 | 任务图、依赖版本、当前进程及恢复位置 |
| Executor（执行器，程序） | 按类似生成器的 next() 推进当前任务进程，记录每轮结果，返回继续、交接或 done | 当前进程的执行帧与客观完成条件 |
| TaskProcess（任务进程，A/B/C/D） | 保存该任务独立的输入、局部过程、材料选择和输出 | 仅本任务；可消费明确指定的上游交付 |
| Worker（进程内的工作执行者） | 在当前进程内部调用模型和工具，完成具体工作 | 当前任务最小上下文 |

这里的进程、线程是任务执行的逻辑边界。可以使用 Rust async task 与独立执行帧实现，首版无需为每个 Flow 节点创建操作系统进程或额外模型配置。每轮模型调用是该进程内的一次工作调用，局部历史归该进程保存。

执行器的 next() 推进当前进程的一轮工作，不自行决定把 A 换成 B。调度器依据组织者决策选择/创建当前进程，然后调用它的执行器；done 或交接结果回到调度器，再由组织者决定下一步。计划中的 A/B/C/D 允许运行时增删和调整，保持未执行任务的动态性。

任务切换与图修改必须在可提交的边界落实：当前模型响应或工具结果已归档后，切换指针并创建新输入。长工具执行期间可接收待应用决策；需要中断时走现有取消机制，先明确副作用结果，再切换，避免当前调用落入另一个任务。

### 2.2 输入输出边界

对 B 来说，A 只是一份明确交付：做完了什么、产生了哪些 B 所需的值，以及交付身份和版本。A 的目标拆解、工具记录、推理和试错留在 A 的局部历史；B 不默认阅读它们。交付可包含地址、接口定义、代码材料引用等具体值，选择范围由 B 的实际工作需要决定。

正常情况下保持封装。发现上游问题，B 返回指向 A 交付的具体问题；组织者通过调度器回溯到 A，执行器在 A 自己的上下文里处理。B 不自行吸收 A 的过程并同时做两个任务。

| `src/request_context.rs`、前端 Flow | 请求调试与流程展示 | 每个节点显示实际输入、输出、版本、交接原因及回溯 |

需要优先处理的具体问题：

1. `agent_service.rs` 在 `scheduler.done()` 时先调用 `activate_next()`；如果已有队列，可能绕过组织者的完成交接决策。
2. `enqueue()` 禁止恢复 Done 工作，现有提示词也禁止重开；缺少明确的“上游输出错误 → 组织者回溯”协议。
3. `scope()` 目前主要由 node_id 与 work_id 组成；重新执行同一节点必须加入执行版本，避免旧局部历史被当作当前过程。
4. `worker_input()` 虽然投影上游结果，但还包含较宽的 modified_files/checks/versions 等内容。应按当前需求选择交付字段，完整记录供按需查看。
5. 树的父子边与调度器的上游依赖分别生成；启用 TaskTree 时 Flow 需要同时表达任务归属和执行顺序。
6. 无进展 continue 限制已有基础。仅换材料 ID、改写结论或改提示不能被当作实际进展，须核对内容和版本。

## 4. 数据契约：复用现有结构，增量改动

### 4.1 节点与执行帧分开

- `node_id`：稳定的任务身份，Flow 中同一个 A 始终是同一个节点。
- `revision`：该节点第几次执行，A@1、A@2；每个执行版本有独立 WorkFrame 与不可变输出。
- `work_id`：现有工作包 ID，可继续作为执行实例 ID，与 node_id/revision 关联。
- `current`：唯一激活的执行实例，不能同时让 A、B 活跃。
- `plan_revision`：当前计划版本；回溯作废旧下游后递增，旧计划事件不能激活新计划任务。
- `rewind_record`：记录唯一事件 ID、发现问题的来源节点、回溯目标、原因、时间、计划版本及作废任务 ID，不维护回到旧下游的 resume_stack。来源节点与回溯目标分别记录，便于统计问题在哪被发现、回到哪返工。
- 任务进程可复用现有 WorkFrame 扩展，保存独立的消息引用、材料选择及结果；执行器只操作显式传入的当前帧，避免持有可混入所有节点的可变聊天。

状态沿用 `ready → running → done`。阻碍、需拆分、上游错误是一次交接的 outcome，或实例的附属信息，不再增加 VERIFYING、WAITING_OBSERVER 等生命周期状态。done 只表示这个执行版本达到自己的完成条件；被替代的历史版本仍保留记录。

### 4.2 Worker 输入

在现有 WorkOrder 上补齐明确的输入引用：

```json
{
  "node_id": "B",
  "revision": 1,
  "goal": "在已启动的应用中打开示例 PPT",
  "done_when": "应用状态确认文稿载入并出现幻灯片",
  "constraints": ["使用上游提供的地址和已有进程"],
  "dependency_inputs": [
    {"node_id": "A", "revision": 1, "fields": ["app_url", "process_id"]}
  ],
  "finding_ids": [],
  "material_ranges": []
}
```

字段名可与现有 API 对齐，关键是依赖必须绑定明确的节点输出版本，并允许选择当前所需字段。输入包括：当前目标、必要的总目标边界、约束、选定上游交付、材料位置，以及当前帧内的实际操作和检查错误。

禁止默认注入全局旧对话、其他分支的源码和过程、已完成节点的工具试错、旧版本相互冲突的结论。共同约束允许保留，普通历史不作为新的指令。

### 4.3 Worker 输出

扩展现有 yield_work 返回协议：

```json
{
  "node_id": "B",
  "revision": 1,
  "outcome": "upstream_problem",
  "summary": "给定地址属于其他应用，无法加载示例",
  "exported_data": {},
  "upstream_problem": {
    "node_id": "A",
    "revision": 1,
    "field": "app_url",
    "reason": "返回页面与目标应用不符",
    "material_ids": [123]
  }
}
```

outcome 只需 `completed / blocked / need_split / upstream_problem`。文件改动、检查退出结果、源码版本等由程序填写，不能相信模型自报成功。发现上游问题时 Worker 返回事实和目标引用，不自行切到 A。

自动完成的 write/check 节点，程序可从写入结果、检查结果及已有当前结论生成输出，不追加一轮“我做完了”的模型调用。输出包含简短 summary、下游需要的 exported_data、材料/结论引用；完整 operations 作为审计资料保存，不批量传下游。

## 5. 实现顺序与交付要求

### 第一步：固定节点身份、输出版本及持久化

主要修改 `work_scheduler.rs`、`flow_tree.rs`，必要时复用数据库/事件存储。

- 建立稳定节点到最新执行版本的映射；保留旧执行输出，避免覆盖历史。
- 将完成事实、当前指针、激活实例、依赖版本、计划版本和回溯记录纳入同一状态快照。
- 调度器是执行状态的唯一来源；TaskTree 管理目标层级，展示状态从调度事实投影。
- 记录一次原子交接事件/快照，确保不能出现指针已切换但输入还属于上一节点的半状态。
- 重启后恢复到已提交状态；正在执行的有副作用工具先核实结果，不盲目重放写入或进程启动。

交付：现有普通单节点工作仍可运行；节点身份稳定，输出引用可区分 A@1 与 A@2。

### 第二步：统一程序交接循环，组织者决定下一节点

主要修改 `agent_service.rs`、`work_scheduler.rs`、`work_organizer.rs`，建议新增 `work_executor.rs` 并在 `main.rs` 注册模块。

先明确程序接口，随后逐段提取现有逻辑，避免重写所有工具：

```text
Scheduler.apply(decision)       校验并创建/调整/选择任务进程
Scheduler.current_process()    返回唯一当前进程
Executor.next(process, runtime) 推进当前进程，返回 done + 可选交接原因 + 结果
Scheduler.accept(tick)          归档当前版本事实及交付，判断是否交给 Organizer
Organizer.decide(snapshot)     根据任务概览和当前交付决定下一步
```

`done=false` 的普通执行继续驱动同一个进程，不自动调用组织者；遇到 need_split、upstream_problem、blocked 等交接原因时可提前 yield。完成条件仍根据真实写入和当前版本检查判定。执行器不管理全局队列，不创建兄弟任务；调度器不自行拼装模型推理结论。

将分散的完成、yield、激活逻辑汇聚为一个交接入口：

```text
收到工具事实或 Worker 返回
→ 校验当前 node/revision
→ 判断本节点完成条件 / 交接原因
→ 持久化当前输出或暂停位置
→ 结束当前帧的模型执行
→ 用浓缩过程调用 Organizer 一次
→ 在临时状态上校验决策
→ 原子提交指针、输入引用、版本及 Flow 事件
→ 构建新 Worker 上下文并执行
```

- 去掉“完成后直接 activate_next 跳过组织者”的路径。组织者可以确认使用已排队任务，无需重新制定全部计划。
- 一次完成/阻碍只产生一次交接，用事件身份去重；失败重试不重复提交状态。
- `continue` 只用于当前未完成的同一任务；新任务、拆分和回溯使用对应的明确决策。
- 已完成帧停止后续发散；如果一个响应包含多个工具调用，执行前逐个校验当前帧，达到完成条件后不再启动旧帧的额外调用。已经在执行的副作用要等待明确结果并归档，避免丢失操作记录。
- 普通实现和检查错误继续由 Worker 在同一帧内修复；不每轮转给组织者。

交付：A 完成 → Organizer 收到 A 输出 → 程序激活 B；没有绕过交接的备用路径。

同时应能定位到明确的单进程执行器入口：其测试/调试输入是一份 TaskProcess，结果属于同一 node/revision；全局任务选择和创建只能经调度器落实。

### 第三步：以执行版本重建 Worker 上下文

主要修改 `agent_service.rs`、`task_notebook.rs`、`worker_work_state.rs`，核对 `notebook_worker_request()`。

- 使用 `node_id + revision + work_id` 标识 scope，旧帧消息始终保留在审计历史中。
- 节点切换时重新构建模型请求，而非向同一个长聊天追加“现在开始 B”。
- A 的原始材料存于 notebook；B 起步只拿选定交付和自己的必要材料。
- 材料恢复必须先清空当前选择，再加载 B 自己的选择；不继承兄弟节点工作集。
- 当前帧正在实现时，所需源码不会仅因汇报一次就消失；材料库容量与模型当前输入预算分开。
- 版本已变更时刷新受影响源码和结论，标记旧结论为历史；未经确认的冲突作为当前明确问题，不能把两条都当作现行事实。
- 回溯后新派发的下游任务使用新的工作 ID 和新计划版本，输入由组织者重新选择；不恢复旧 B 的局部聊天、错误、完成标记或任务队列。需要旧材料时以明确引用和现行版本重新选择。

交付：请求调试可以证明 B 中没有 A 的试错过程，仅有选定 A 输出及必要约束。

### 第四步：显式回溯、作废全部旧下游并重新规划

主要修改 `work_organizer.rs`、`work_scheduler.rs`、`flow_tree.rs`、`agent_service.rs`。

给组织者增加明确的 `revisit` 决策，内容包括目标节点、被质疑版本、具体修复目标及必要事实引用。程序固定执行“回溯并作废旧下游”，不提供恢复旧下游的返回节点。

流程：

1. 当前节点返回 upstream_problem，程序归档当前实际结果并交接。
2. Organizer 判断是 A 的交付错误、B 的使用方式错误还是外部条件变化。能在 B 修复的继续 B；确需修复 A 的提交 revisit。
3. 程序校验回溯目标与版本，定位它在当前有效计划中的位置；将它之后的所有旧任务作废，移出执行队列和有效任务集合，但节点及原有连线继续保留在 Flow 画布中，灰色表示废弃。包括待执行、暂停、执行中以及已完成的下游任务，不能仅作废直接依赖它的节点。
4. 递增 plan_revision，创建 A@2，并激活它。仅注入 A 的修复任务、被质疑交付及必要材料，旧下游过程不进入 A。
5. A@2 完成，A@1 交付标为历史；Organizer 根据新交付从这里重新布置后续任务，例如 A@2 → E → F。即使新任务目标仍叫 B，也使用新的任务实例和输入。
6. 不返回旧 B，不自动重跑旧 B/C/D，也不保留旧下游为可继续执行的队列。

作废范围按当前有效计划的执行顺序和回溯边界计算，不能仅按节点创建时间或依赖字段判定。树中父节点负责目标归属，执行任务以明确的计划顺序确定哪些属于回溯点之后；不能把包含 A 的总目标父节点一并作废。回溯目标之前的任务保留；目标之后的旧任务即使声明未依赖 A，也全部退出当前计划。

作废作为计划归属信息表达，例如 invalidated_by_plan_revision，沿用 ready/running/done，不增加复杂生命周期。Flow 显示层根据作废信息投影为灰色“已废弃”，即使该节点作废前已经完成也采用废弃样式；详情保留作废前状态。历史节点、请求、材料和结果保留以便审计，但不再参与 all_done、依赖满足、总目标汇总和 Worker 默认上下文。总目标在新计划的实际工作完成前保持未完成。

当前执行中的旧下游先按取消及副作用归档规则结束，再提交回溯；所有事件携带 node/revision/plan_revision。旧计划晚到的工具或模型结果只能归档，不得恢复队列或覆盖新指针。

回溯不等于自动撤销文件。可能已有用户修改或其他已完成任务的副作用，不能全量 undo。需要撤销时给出具体恢复范围，使用现有工具和权限处理。重复回溯却没有新的事实或结果时有界终止并报告阻碍。

交付：例如原计划 A → B → C → D，在 C 回溯到 A 后，旧 B/C/D 全部作废；有效计划变为 A@2 → E → F，由组织者重新派发。任何请求始终只有一个当前任务，没有 A/B 混合帧。

### 第五步：组织者的浓缩视野与 Observer 协作

修改 `organizer_system.md`、`worker_unit.md`、`work_organizer.rs` 及相关输入组装。

组织者输入：用户总目标、计划概览、节点最新状态和输出版本、当前交接结果、直接相关上游交付、未解决条件、材料目录、相关 Observer 建议。完整日志和源码按引用保留，不默认塞入。

- 派发的每个任务要能直接执行；缺少必要事实时明确安排一个小调查任务，已知条件足够时直接实现。
- 对收到的结果决定下一步，先完成当前任务，允许动态调整下游或拆分子任务。
- 结束必须覆盖总目标的实际交付和必要子任务；尚未执行的用户要求不能通过删掉计划节点被当作已完成。
- Observer 观察真实节点状态和交付；关于当前节点的建议进入当前输入，关于后续计划或上游问题的建议交给组织者。
- 组织者接收建议后落实为一次任务调整或一次理由记录；Worker 无需为了回复建议单独空转。
- 停滞只在新的有效窗口触发；用新源码版本、真实修改、新检查结果或实质新增信息判断进展，改写汇报不能清零。

同步检查 tool schema、提示词、Rust action 校验。避免提示词允许 revisit，工具枚举或主循环却不支持。

### 第六步：Flow 和上下文调试显示真实交接

修改 `frontend/src/model.ts`、`FlowView.tsx`、`TaskNode.tsx` 及其样式、请求调试映射。

- 展示总目标和 A → B → C 的执行顺序；父子边表示归属，依赖边表示交付，两者明确区分。
- 当前仅一个执行节点高亮；父节点可显示整体进行中，但不表示父节点也在调用 Worker。
- 同一回溯节点展示最新 revision，可展开历史执行；回溯显示原因、来源节点、目标及作废范围。旧下游节点和原有连线默认继续显示在画布中，使用灰色及“已废弃”文字标识；新下游显示组织者重新派发的任务。保留布局位置，以便直观看到原路径在哪中断和新路径如何展开。
- 后端 Flow 投影必须包含当前任务和废弃历史任务；replaceCurrentTurn 或重新生成 flow/plan 不得删掉废弃节点、覆盖旧任务实例。新任务使用唯一身份，避免同名节点合并。废弃节点可查看输入、输出、工具记录及废弃原因，其执行/继续操作不可用。
- 用回溯连线或事件标记表示“发现问题的节点 → 回溯目标”，保留对应节点/版本。节点详情汇总被回溯次数、发现上游问题次数和最近原因，按唯一事件 ID 去重。被连带作废不自动计为该节点出错，组织者发起回溯也不自动等同于已确认缺陷。
- 节点详情展示本次派发目标、完成条件、选定上游输出、材料引用、实际结果，以及关联的真实模型请求。
- 节点/版本切换后正确归属工具事件、请求、结论，保留已有详情关闭交互。
- UI 状态从后端事件产生，不凭消息中“已完成”或 turn/end 给未完成节点标绿。

交付：Flow 是实际调度状态的投影，能看到任务如何交接和回溯。

## 6. 验收场景

实现者应在获得运行验证授权后进行以下验证，并提供实际请求和事件记录。编译通过不能替代场景验证。

| 场景 | 必须出现的行为 |
| --- | --- |
| 简单技术问答 | 单节点直接回答；不无故读取代码或先跑调查阶段 |
| 已有精确材料的小修改 | 直接派发实现节点，实现与检查在同一帧完成，检查成功后不再反复查 diff |
| A → B → C，初始已经排队 | A 完成仍交给组织者判断，然后才激活 B |
| 上下文隔离 | B 请求仅有当前任务与指定交付；不含 A 的调查、失败日志、旧建议和其他分支源码 |
| 执行器和调度器分工 | next() 只推进当前进程；组织者经调度器创建/切换任务，执行器不自行跳到兄弟节点 |
| 动态调整未执行任务 | A 交付改变后可新增/替换后续任务，已有当前调用结果仍归属原 node/revision |
| 普通检查失败 | 当前节点内修复、重新检查；不强制新节点和组织者调用 |
| 当前节点发现 A@1 错误 | 明确交接，旧下游全部作废，指针移到 A@2；组织者根据新交付重新安排任务 |
| 同一节点旧版本晚到的事件 | 不修改当前新版本的完成状态或结果；保留为对应版本的审计事件 |
| 回溯影响下游 | 目标之后所有旧任务退出有效计划，包含已完成及声明无直接依赖的任务；目标之前保留；不自动全工作区撤销 |
| 回溯后收尾 | 旧下游不参与 all_done、交付汇总和依赖满足，旧计划晚到事件不能推动新计划；总目标等待新任务完成 |
| 废弃任务可见 | 回溯后旧下游节点及连线继续在 Flow 中灰色显示，详情可读；刷新页面或重建计划不丢失，也不能继续执行 |
| 问题路径统计 | 可区分问题发现节点和回溯目标，重复事件不重复计数，连带废弃节点不被误计为故障节点 |
| NeedSplit | 当前问题保留，组织者建立具体子任务，完成后明确返回或汇总 |
| 无新信息、重复 continue/revisit | 有界交接，给出具体阻碍；报告改写不算实际进展 |
| 中断及重启恢复 | 已完成结果保留，恢复单一指针，不重复启动服务或盲目重放写入 |
| 启动项目并打开示例 | 总目标下至少区分启动就绪与加载文稿两个交付；无浏览器能力时剩余部分明确未完成 |

最低交付证据：一个正常 A → B → C 流程、一个在 C 回溯到 A 并作废旧下游、重规划为 A@2 → E → F 的流程、一个直接回答流程。每个提供节点输入输出、组织者决策、指针事件和上下文截图/请求记录。统计工具调用和组织者调用次数，解释每次交接原因；不以固定次数限制代替正确调度。

## 7. 实施边界与交接给下一位 AI 的指令

请按上述顺序增量实现，先让节点交接和回溯在后端成立，再接前端显示。复用 WorkScheduler、TaskTree、Notebook 和当前工具；保持 ready/running/done，不另建复杂工作流框架。

本计划聚焦组织、上下文与状态同步。项目进程就绪和浏览器工具可作为真实场景依赖，先检查最新实现，不把它们再次混入调度器大改。

不要强制所有任务先读源码，不要每次工具调用都请求组织者，不要让 Observer 成为审批者，不要以“催 Worker 赶快动手”的提示词代替交接机制，不要让已完成的旧版本重新污染新任务。

实施报告须区分：已经实现的源码、编译检查结果、实际运行场景、未验证能力。加载新版本或停止现有 Agent 前确认当次用户授权及正在运行的任务，避免中断他人的工作。
