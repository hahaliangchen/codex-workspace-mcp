## 1. 上游从需求到交付的完整流程

下表描述此次固定版本的 **Default Generate**。它有独立的 Quick 路线，但必须由明确的快速/跳过策略意图触发，不能因任务长或执行困难偷偷切换。

| 阶段 | 输入 | 工作及输出 | 确认点／进入下一阶段的条件 |
|---|---|---|---|
| 0. 路由 | 用户目标、已有文件、生成/改稿/制模板意图 | 确定 Generate、Create Template 或 Edit Native；Generate 再确定 Default/Quick 等具体流程 | 请求明确时直接路由；确实有歧义才问。不同路线不能混用执行指令 |
| 1. 材料与事实准备 | 主题、附件、网页、已有 PPT、约束 | 阅读/转换材料；有事实缺口才补充研究；得到可追溯的内容材料和必要资产 | 内容足以策划；不能用编造数据填补事实缺口 |
| 2. 项目初始化 | 内容材料、用户已明确的画布等条件 | 建立项目，导入原始材料及提取资料 | 项目及必要来源可用。技术初始化不是生成完成 |
| 3. 模板候选准备 | 用户指定模板或可用模板目录 | 准备模板/自由设计选项，保留准确来源 | 内部准备，无额外停顿；模板不能反过来改变用户目标 |
| 4A. 策划第一阶段 | 用户目标、材料、候选模板 | 明确受众、传播目的、希望受众得到什么、核心信息、使用场景、交付用途；同时确定页数范围/画布及模板选择 | 用户确认沟通目标和模板选择。已确认值不得被后续模板替换 |
| 4B. 应用模板及方案选择 | 第一阶段确认、实际模板内容 | 安装模板的项目副本，读取规则和原型，形成完整设计方向及图片/字体等建议；上游通常提供三种设计方向 | 用户确认最终方案。上游显式授权代决策时允许相应简化，不能伪造用户确认 |
| 4C. 落地设计说明与逐页计划 | 最终确认、来源内容 | 写完整 `design_spec.md`；§IX 是有序页清单，每页含核心信息、读者所得、内容关系、支撑内容、视觉/素材需求。再从它导出 `spec_lock.md` 的执行约束 | 先核对说明忠于确认，再核对执行约束忠于说明；完整说明的额外用户复审是上游可选项，不应误说为其所有任务都强制弹一次大纲确认 |
| 5. 素材准备 | 大纲中的素材职责、允许的来源 | 准备已有图片、生成/检索素材、切片或衍生图，形成真实文件及状态清单 | 进入制作前资源有明确状态；必需资源缺失不能悄悄删掉该视觉要求，最终交付不能遗留未解决占位 |
| 6A. 正式制作 | 已确认说明、有序页清单、执行约束、可用素材 | 主执行者依次设计页面；上游作者语言是 SVG，页面包含完整可见设计，模板和说明不会在导出时自动补内容 | 每个计划条目对应最终页面；不在画图时擅自换大纲或靠复制模板凑页数 |
| 6B. 早期与最终质量检查 | 实际页面与完整计划 | 较长稿在前五页后检查方法性问题；完成全稿后集中检查、汇总修复、复验；核对计划要求的视觉表达是否实际出现 | 几何/素材/计划覆盖满足条件。重复出现的问题要改方法，不能只调整一张样本 |
| 6C. 条件性检查和附属内容 | 图表、配音/讲稿/动画需求等 | 图表核查、讲稿、动画等按需执行。另有真正逐页看图的视觉审查流程，携带计划、PNG、页角色与规则，逐页保存结论 | 上游逐页视觉复审默认需要用户明确启用；本项目用户已要求视觉闭环，应作为交付必需，不照搬其可选默认 |
| 7. 导出与交付后核验 | 当前页面、匹配当前源文件的最终报告、必需素材 | 生成原生 PPTX，输出文件及 postflight 报告；校验包结构、页数、资源和报告对应关系 | 导出器拒绝过期/缺失的必需质量报告；成功创建文件仍须与最终稿版本对应 |
| 8. 修改与恢复 | 已交付稿或中断稿、持久计划、用户新要求 | 局部文字改动修改页面及受影响的计划项；增删页先更新页清单；中断后从计划和实际产物恢复到具体位置 | 不凭聊天摘要重建原任务；不为局部改字重跑全部策划；变更确认过的范围必须保留真实授权 |

上游还有模板制作前置闭环：**读取参考材料 → 提炼品牌/样式/布局事实 → 用户确认模板方案 → 制作模板及资产 → 校验 → 原型审阅/必要的 PPTX 读回 → 发布或登记 → 生成时消费项目副本**。模板页数不是输出页数政策，品牌模板可以只有身份资产而没有页面骨架。

主要来源：下载副本的 `workflows/generate-pptx.md`（11、101、156、183、223、247、261、318 行附近）、`references/plan-core.md`、`references/strategist.md`、`workflows/stages/resume-execute.md`、`workflows/create-template.md`。

### 策划为何被丢掉：已证实的改写链

1. 原入口虽然采用后来被用户否定的骨架填充方案，但**策划、逐页提案、确认、commit_design_spec 原本存在**。
2. 本次改成 HTML 时，当前未提交 diff 整段删除 `User confirmation comes before generation`，也删除 `Making a new deck` 中的方案保存步骤。
3. 新入口优先列出了 HTML 合约、品牌保护和页面工具，没有补回等价的规划前置阶段。
4. `references/strategist.md`、设计说明参考和 `commit_design_spec` 工具仍在，主入口必读清单却不再指向它们；这是流程断开，而非能力从未存在。
5. 后续围绕提前停工、裁切、视觉检查的修复没有纠正这个入口错误。因此测试不断在不完整的生产协议上追局部结果。

这是本次实施的判断和改写问题。不能归因于用户没有说清楚，也不能仅归因于模型不熟 PPT。恢复时应保留策划，把被否定的固定骨架/自动排版替换为 HTML 自由设计；不能把整个旧入口原样还原。

## 3. 改造主线、工具与状态归属

唯一生成主线：

**需求确认 → 逐页大纲草稿落库 → 用户确认大纲版本 → 按大纲准备素材并逐页 HTML 设计 → 对照大纲逐页验收 → 导出并核对交付文件。**

以下“新增／扩展”均为方案，尚未实现或部署。

### 最小数据边界

1. **Agent 主任务记录**：root_task_id、原始需求、明确的主任务修订、模板 pin、计划 ID/确认版本引用。只有主任务拥有它；临时步骤和子任务不建新主目标。
2. **PPT 计划记录**：一份带版本的大纲及共享设计说明，含 pages[] 和 target_page_count、用户确认凭据。现有 `SysPptDraft.Design/Outline`、design_spec.md/outline.md 可保留为兼容展示/导出，必须从同一计划生成，不能各自成为不同真相源。
3. **PPT 执行/验收记录**：计划页与真实页映射、生成保存事实、必要素材状态、各检查状态、问题及证据引用。无需新造通用工作流平台，也不保存每次临时思考为任务。
4. **PPTX 文稿与资产**：继续使用现有文件/对象存储和文稿版本；不新增第二份长期设计 JSON。主任务/大纲/验收是业务元数据，不等于把编辑器设计 JSON 另存一份。

建议的逐页可见状态：`未生成 → 已创建页面 → 内容已保存 → 待验收 → 需修复 / 验收通过`。检查再分“内容覆盖”和“视觉合格”，并显示已确认大纲的目标数量，例如“计划20页，已写18页，已验收12页，待修2页”；每一个数字必须由对应记录计算。

### 大纲要求与设计自由

每页只规定应传达的意义、必要信息和资产职责，不规定坐标、三列卡片、固定槽位或自动布局。例如“解释需求变化如何挤占测试时间，给出机制链和一个明确标为示例的场景”属于内容要求；采用横向时间轴还是前后对照由 HTML 设计决定。

Logo 默认固定；原模板中的总结图只有明确标为 reference/可变才允许重画。空白品牌模板只约束固定资产与品牌规则，其余区域自由设计。有布局的模板可以复用或轻改，不强制填骨架。目标页数由任务和已确认页纲决定，不由模板页数或五页测试样本决定。

### 模板制作与生成的接点

先用一个联通模板完成：上传 → PPTX/JSON/HTML 检查 → 确认固定/内容/参考用途 → 保存模板说明和版本 → 独立试生成 → 大纲确认 → 完整生成/验收/导出 → 发布。生成读取已发布快照，试生成不改源模板。成功后再根据实际通过的路径写转换标准，交给其他人转换模板；不在此轮迁移全部旧模板。

## 4. 主任务上下文策略

按用户要求，固定块与可压缩过程严格分开。

| 类别 | 保存内容 | 每轮如何使用 | 压缩政策 |
|---|---|---|---|
| 主任务固定块 | 用户原始任务及明确修订；选中模板 ID/版本/哈希与固定约束；目标页数；整份已确认的逐页简纲及计划版本 | 宿主从独立持久记录组装，模型实际请求发送前注入；预算必须计入；不是从摘要恢复 | 永不参与过程压缩。不能只保留一个“去读大纲”的路径代替固定页纲 |
| 真实进度块 | 当前文件版本/页数；计划页映射；已写、待验收、需修复、有效通过的页面；素材与导出状态 | 宿主读取最新持久记录和项目状态后注入；失败明确 unknown；不能沿用旧的 verified 状态 | 随时可重建，不交给模型记忆，不把它写成主目标原文 |
| 当前工作材料 | 当前页 HTML、对应计划内容、所需素材、具体错误及截图 | 按需读本轮需要的材料；大文件保存引用及原始证据 | 可以压缩、引用化、移出活动窗口，之后仍可按引用恢复 |
| 历史过程 | 旧版 HTML、重复错误、已解决问题、旧截图、工具日志、临时修复步骤 | 主要用于需要时审计，正常恢复不全量重放 | 可以压缩，不把其生成的步骤提升为主任务 |

具体边界：

- 主任务只指“用所选模板完成用户确认的这份演示文稿”。“重试第8页”“修一个节点”“检查最后两页”是执行步骤，不新建固定目标。
- 用户明确修改主任务范围时更新主记录和相应计划版本；状态询问、临时排查、普通“继续”不自动变成新的主任务内容。
- 子代理只领当前工作分配，并读同一主任务及计划版本；不能改写主目标或自报整稿完成。
- 模板说明、大纲中的来源材料和工具输出须保留来源属性，不能变成覆盖宿主权限的系统命令。
- 再次压缩、页面刷新、Agent 重启后，固定块应完全相同；进度由当前文件和验收记录恢复。失败恢复不重新生成用户目标，也不依赖模型回忆上次做到哪。
- 对目标和计划的保护不能靠“总结得更好”。过程压缩器不再负责保存这些信息；它只整理当前材料、未解决过程问题和证据引用。

## 5. 改造顺序与验收边界

先完成流程，随后再做质量细调；当前报告不授权自动开始实现。

1. **先修唯一 skill 入口**：恢复策划和已确认页纲前置阶段，清理相互矛盾的旧执行指令。Anthropic 审美原文保留；PPT 设计执行统一 HTML。
2. **再接计划保存与确认**：复用 commit_design_spec，独立目标页数；计划版本和真实用户确认可追溯；未确认计划不能生成正文。
3. **再接主任务固定注入与真实进度**：只有需求/模板/页数/已确认大纲常驻；进度从系统事实计算；过程可压缩。
4. **再接按页验收和完成条件**：内容对照大纲、图片/图标到位、文字完整、品牌保护、当前视觉结论；导出绑定被验收的版本。
5. **最后验证一个模板的完整流程**：分别做短稿和20页稿，测试大纲修改/确认、中断恢复、手动改稿后AI续改；都通过后再发布标准，不先扩展更多模板或新功能。

必须通过的用例：

- 大纲已显示但未确认，刷新后仍保持待确认，不生成正文；旧版本确认不能批准新版。
- 计划20页时，保存1页或复制20个空模板不会改变目标或显示完成。
- 每页能追溯到一个计划条目；遗漏内容、缺必要素材或视觉不合格都会留在待修列表。
- 连续压缩及服务恢复后，主任务和已确认页纲不丢；临时修复步骤不进入主目标。
- 局部手动改字/移动后AI继续，只在授权范围内改最新HTML；旧检查不会批准新稿。
- 修复之后的新图重新验收；不能用旧图、旧大纲或单纯成功状态宣布完成。
- 最终导出文件与验收版本一致，来源模板及Logo保持。

## 6. 不能照搬的上游机制

- 上游 SVG 作者语言、Python导出脚本、原生 OOXML 编辑路线不进入本产品的模型操作路径；继续 HTML ⇄ 内存JSON ⇄ PPTX。
- 不把上游 Brand/Style/Layout/Deck 分类、三种设计方向、所有确认表单机械搬成复杂产品交互；按用户指定主线保留必要决定即可。
- 上游 Quick 可省策划、视觉复审可选；本产品当前要求“大纲落库并经用户确认”和“逐页验收”，因此不能用这些分支绕过要求。
- 上游模板部分严格结构/槽位策略不能覆盖用户允许自由构图的要求；只强制真正的品牌固定项和明确内容约束。
- 上游默认视觉审查有迭代次数与人工接手边界；我们的修复后复验、通过条件及真正阻塞必须一致，不可从“没有继续检查”推断成功。
