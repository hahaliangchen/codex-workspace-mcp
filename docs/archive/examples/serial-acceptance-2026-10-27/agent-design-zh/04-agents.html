通用 Agent 设计 / 执行与协作
协作模型 · 第 04 页

并发不是“多开几个任务”
而是明确分工与交接

当工作可独立拆分且已获授权，主 Agent 可以 fork 一个子 Agent 并行执行。join 只收回函数结果；主 Agent 仍需根据实际工作区检查、整合文件，并验收真实产物。

一个主 Agent + 一个子 Agentfork → join → 整合 → 验收共享目录与 Git worktree
本页导览协作顺序谁负责什么两类工作区Git 交接步骤整合后的验收容易混淆的边界

本页聚焦并发 Agent 的职责划分、工作区所有权与文件整合。它们不是隐藏在 join 后面的自动行为，而是流程必须显式表达并用实际结果完成的工作。

01 / SEQUENCE从独立分工到可交付结果

先准备公共要求和材料，再把不重叠的任务分给两路。并发执行结束后，主 Agent 负责将分支成果纳入自己的工作区，逐项读回并验收。

01 · PREPARE主 Agent 准备整理共享要求、实际源材料与各自的任务清单。
02 · FORK启动两路先后调用 fork；公共材料相同，独占职责不同。
03 · JOIN收齐结果join 按句柄顺序返回函数结果，不搬运或合并文件。
04 · INTEGRATE主 Agent 整合按句柄工作区信息决定检查并合并，或沿用共享目录。
05 · VERIFY读回验收读取实际产物，对照目标检查；失败时处理并复查。
关键区别：join 代表分支函数已返回，不代表分支文件已出现在主工作区，更不代表业务产物已经通过检查。

02 / OWNERSHIP分工要互补，交付要可追溯

主 Agent

组织公共输入，拥有整合与最终验收

准备共享材料和各路独占任务；启动并等待分支；检查分支工作区与改动；整合后读回实际文件，按要求检查并负责如实交付。

子 Agent

只完成明确分配的那一部分

使用显式传入的公共材料，完成自己的 assignment，并返回实际结果。分支的局部对话不会整份复制给父任务；所需证据应由返回值或稳定引用明确交接。

数据流示意 · 两个实参分别绑定
const a = fork(work, shared, leftAssignment);
const b = fork(work, shared, rightAssignment);
const results = join(a, b); // [a 的结果, b 的结果]
integrate(a);
integrate(b);
// 再读回实际产物并逐项检查

每个分支收到相同的 shared 和不同的职责清单。fork 使用 work(shared, assignment) 的两个位置实参，不会自动打包成一个输入信封。独占分工有助于减少覆盖冲突；分支结果仍由主 Agent 核验。

03 / WORKSPACE工作区模式决定文件如何到达主任务

SHARED · 共享目录

同一目录，不需要 Git 合并

在普通共享目录中，分支使用共享工作区。join 后可以在该目录检查文件；仍需读回和验收。跳过的是 Git 整合，不是业务检查。

GIT_WORKTREE · 独立工作树

分支目录隔离，需要显式整合

Git 可写项目中的分支在独立 worktree 工作。分支文件不会仅因 join 而自动出现在主目录；应按句柄的 integration_required 和实际路径处理。

fork 句柄提供宿主实际分配的工作区信息，包括模式、路径与是否需要整合。分支返回的相对路径以其工作区为基准；在 Git 分支尚未合并时，不能拿同一路径直接读取主目录并假定文件存在。

Git 派发前提：从仓库根目录和干净、已提交的基线启动。先 fork 所需分支，再进行主 Agent 自己的新写入；否则脏工作树可能使后续 fork 被拒绝。需要子 Agent 使用的新材料应在 fork 前准备好并明确传入。

04 / GIT HANDOFFGit worktree：先检查差异，再合并

  1. 检查真实句柄确认工作区模式、实际路径和 integration_required；不要凭“用了 fork”推断一定要合并。
  2. 检查分支改动需要 Git 整合时，使用句柄中的 agent_id 检查实际差异，核对改动是否属于该分支的分工。
  3. 按检查到的 head 合并将检查结果中的 head 用作合并期望版本；由宿主执行分支合并，而不是手工复制文件模拟成功。
  4. 回到主工作区读回只有整合成功后，才从主工作区读取分支产物。冲突、整合失败或状态未知时停止并如实处理。
流程概念示意 · 以当前工具契约为准
if (handle.workspace.integration_required) {
  const changes = host.inspect_agent_changes({agent_id: handle.agent_id});
  host.merge_agent_result({
    agent_id: handle.agent_id,
    expected_head: changes.head
  });
}
// shared 模式不做 Git merge；两种模式都继续验收。

检查与合并是显式流程步骤，不是 join 的隐式副作用。若分支差异不符合预期、合并冲突或宿主返回失败，不能把“子 Agent 返回了结果”包装成整合成功。

05 / ACCEPTANCE整合完成后，验收真实产物

主 Agent 应从正确的工作区读回实际文件，再按用户目标和适用技能检查内容与结构。工具受理、函数返回、正确的文件数量或 Git 合并成功，都不能单独证明内容符合要求。

文件来自已确认的工作区，并且确实可读。
每份产物对应分配给它的具体职责。
内容忠于传入材料，未把历史测试结果说成当前事实。
检查结论基于读回的实际产物和适用的验收标准。

若同一个验收 AI 函数发现可修复问题，应在自己的上下文中依据问题证据处理，随后重新读回实际对象并复查；复查未通过就停止交付并报告具体原因。不能用修复者的自述替代独立的实际复核。

视觉边界：文本读回与结构检查不等同于浏览器渲染。没有实际执行浏览器渲染和相应检查，就只能报告已完成的文本／结构验证，不能宣称视觉验收通过。

06 / BOUNDARIES并发、函数调用与 AI 判断各有边界

FUNCTION ≠ AGENT

普通 helper 调用不启动新 Agent

普通函数在当前 Runtime 的局部函数帧执行。只有获授权的 fork 才建立协作分支；有待办清单并不自动意味着应并发。

JOIN ≠ ACCEPTANCE

汇合不是业务成功判定

join 只等待并按句柄顺序收集函数返回。文件交接、实际检查、必要修复与交付仍属于明确的后续流程。

通用宿主提供调用、作用域、持久化、权限、取消和工作区交接机制；具体业务的页数、生产步骤、内容规范和验收要求由用户输入与适用技能决定。并发只能在授权范围内运行，不因共享父环境或传递变量扩大权限。
