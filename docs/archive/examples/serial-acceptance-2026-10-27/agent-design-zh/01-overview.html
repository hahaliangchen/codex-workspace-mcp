通用 Agent：
从目标到交付

一个主任务，一套可执行流程。AI 负责需要理解与判断的工作；Rust 宿主负责确定性推进、工具边界、作用域与恢复。业务怎么做、做到什么算通过，仍由用户目标和适用技能决定。

本项目是由 Rust 执行任务的本地通用 Agent。它不是把任意 JavaScript 交给一个 JS 虚拟机运行，而是用受限的流程伪代码明确表达调用、分支、循环和工具步骤；智能生成、理解与业务判断则通过显式 AI 任务函数完成。

01 · 一个通用执行器，不是一套业务剧本

Agent 面对用户目标，结合可用技能和工具组织工作。宿主把调用持续推进、记录真实请求与回执、管理数据作用域和容量，并在工具或函数返回后恢复程序。宿主不替每个业务规定要做几步、产出几页或使用哪种版式。

01 / 显式流程

顺序和控制流可读

普通函数、条件、循环与数据计算由 Rust 按固定规则执行。流程代码说明“接下来做什么”，而不是让模型凭一段模糊的步骤摘要猜测程序位置。

02 / 智能工作有边界

AI 处理需要判断的任务

内容生成、资料理解和业务验收写成带职责与返回契约的 @virtual 函数。调用时，执行 AI 根据真实参数完成这项工作并返回 JSON。

03 / 工具契约固定

使用已发布的真实方法

流程调用固定的 library.method 与 JSON 参数。编译检查工具是否可用；真正执行仍经过原有权限和插件归属检查。

04 / 业务规则来自业务方

技能与插件定义怎么验收

用户、技能和插件提供目标、业务条件及验收标准。工具受理、程序返回或任务结束都不能单独证明业务已成功。

确定性边界：相同程序、输入及相同工具／任务返回值，会得到相同的普通控制流；这不意味着 AI 判断或外部操作本身是确定的。

02 · 工作流全景

主任务提交唯一 main，Runtime 解释程序位置并在效果完成后继续。简单工作可以串行；只有明确授权且职责相互独立时，才用 fork/join 并发。

目标与准备确认用户要求，准备必要技能、工具契约和共享材料。
提交 main一份程序覆盖工作、验证和交付，不另建步骤调度器。
推进工作宿主计算与调用工具；AI 函数处理需要理解的任务。
收集与核验函数返回或 join 后，检查真实产物与业务证据。
交付结果返回可复用结果和限制；未通过则停止或按职责处理。
用户目标 ↓ 一次主任务 · 唯一 main ├── 普通代码 → 分支／循环／数据运算（宿主确定性执行） ├── library.method(...) → 工具调用 → 保存原始回执 → 恢复原程序 ├── @virtual helper(...) → AI 完成明确职责 → JSON 返回 └── 获授权的 fork(...) → 独立分支 → join(...) → 必要时显式整合 ↓ 真实产物 + 业务检查 + 如实交付

普通 helper 运行于 Runtime 局部函数帧，不会因为函数调用就启动另一个 Agent。子任务与并发分支也不是同一种概念。

03 · 谁负责什么

参与者主要责任不应越界
用户提出目标、约束、授权范围和必要确认。权限不能由工具“可用”或旧对话自动扩大。
AI / 模型理解目标、选择工具和技能、组织任务、处理智能工作，并消费结果。不能把工具成功、模型自述或任务结束直接当作业务验收。
技能与插件提供具体业务流程、工具契约、条件和验收要求。不能改变宿主权限，也不应把业务专用流程伪装成通用宿主规则。
Rust 宿主确定性执行、作用域、工具分发、持久化、容量控制、权限及取消。不替业务决定页数、生产步骤、版式或内容质量标准。
工具与业务后端执行具体操作，返回实际状态、结果、错误与条件。accepted 代表受理，不必然代表工作已经完成。

04 · 流程怎么写，AI 工作怎么表达

版本 12 借用 JavaScript 基础语法的外观，但只支持受限白名单；没有任意 JS 全局环境，也不支持异步函数、生成器、模块、类或 TypeScript 类型。普通算术、比较、逻辑和循环由宿主执行；类型错误等明确失败，不会自动转成 AI 判断。

普通函数：确定性的编排

helper(args) 进入局部 Runtime 帧；函数代码由宿主运行，返回后回到调用位置。文件读取、结果收集和明确的条件分支适合放在这里。

@virtual：明确的智能职责

前置说明写清任务、输入和返回字段。AI 可以在自己的任务上下文中分析或调用真实工具，并按契约返回；注释本身不会执行。

library.method：真实工具步骤

固定库名和自动生成的声明让参数与权限边界清晰。工具原始返回值进入程序；业务层仍需解释和检查。

fork/join：受授权的并行工作

分支只承担明确分开的职责。join 收集函数结果，不自动复制文件、不自动验收，也不保证 Git 分支已经合并。

语言不是完整 JavaScript。例如条件使用项目规定的 C 风格真值，缺失字段返回 null；只可调用已公布的数据方法和固定工具名。实际语法、数值规则和限制应以《Agent 流程伪代码与 Rust 执行器》当前版本为准。

05 · 共享材料，隔离过程

公共依赖先由调用方准备，再以真实参数传入需要它的函数；函数参数按位置绑定。父变量是进入时的值快照，不是对文件或后端的实时订阅。要核验变化后的状态时，按需要显式读取或刷新。

  • 向下共享：技能、权限范围、公共资料和已完成结果可在作用域规则允许的范围内供子函数使用。
  • 局部隔离：函数自己的探索过程和新读材料不会自动复制给父任务或兄弟分支。
  • 返回交接：调用方通过 JSON 返回值拿到摘要、结果和稳定引用；需要具体正文时再读取引用。
  • 按容量管理：运行时折叠旧的完整交换并保留恢复入口；超大材料应分页或使用资产引用，不能把未读正文当成已经理解。
  • 权限不继承扩大：继承可见材料不代表获得额外工具或新的授权。
关键区分：释放函数的活动上下文，不等于删除历史、资产快照或外部产物；局部上下文隔离也不会撤销已经发生的真实写入。

06 · 结果、验收与失败恢复

finish 或函数 return 只表示控制流交接。业务验收要针对真实产物和适用标准；通过与否由明确的检查任务作出判断，并以其返回的布尔结论推进普通程序。

检查实际对象

需要确认文件或外部状态时读取真实结果，再按用户要求和技能标准检查。代码结构正确不等于内容合格；没有浏览器渲染证据时，不宣称视觉通过。

按证据处理问题

允许修复时，把真实问题交给职责明确的处理步骤。修复后重新读回并复查；复查仍失败就停止交付，不把失败改写成成功。

编译失败与运行失败不同

完整源码先编译。源码验证失败时可依据诊断修正同一程序；运行时错误则按异常和已有回执处理，不能假设外部操作没有发生。

不重放未知副作用

恢复时消费已有回执；如果外部操作是否完成未知，明确报告不确定性，不自动重试写入、上传等副作用。

实际文件原始工具回执检查证据 这些是不同的事实来源，不能互相替代。

07 · 维护通用执行层的设计底线

  1. 业务生产流程继续由技能、插件和用户要求定义，不塞进通用宿主。
  2. 调用、控制流、数据和工具契约尽量显式；智能判断走显式 AI 任务函数。
  3. 复用已经提供的输入与回执，不把重复读取历史当成每次工作的固定仪式。
  4. 默认串行；只有职责独立且得到授权时才并行，并在汇合后明确整合与检查。
  5. 任务结束与业务验收分别表达，所有成功声明应有实际产物和相应证据支撑。
  6. 容量不足时保留原件和引用；权限、插件归属、取消和明确确认持续有效。

项目整体还包含本地文件工具、代码符号索引、技能插件、模型与过程记录、浏览器和视觉能力等。它们是通用宿主能力；具体业务如何组合这些能力，应以该任务实际可用的工具声明、用户授权和业务技能为准。
