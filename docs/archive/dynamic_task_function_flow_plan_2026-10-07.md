# 动态任务函数链、组织者与调度器改造计划

日期：2026-10-07

## 1. 目标与执行原则

组织者是 Worker 在任务交接时的工作形态，使用同一 provider、model 和用户选择的推理配置，通过独立上下文决定下一件事。调度器是组织者的工具方法；执行器负责运行当前任务。Observer 在旁路观察组织与执行过程。

主循环为：

```text
组织者决定下一件事
  → 调用调度器创建当前任务节点
  → Worker(当前任务输入) 执行
  → 返回当前任务结果
  → 调度器保存结果并结束该节点
  → 组织者回顾必要的 Flow 产出，决定下一件事
```

Flow 根据执行结果逐个增加节点。组织者可以保留粗略方向，但首版每次只派一个可立即执行的任务，不要求先生成完整树、任务队列或所有后续节点。

一个节点对应一件具有明确输入和输出的任务。节点内部可以调用多次模型和工具，不把每条工具调用都画成一个节点。任务过大、遇到外部依赖或需要回溯时，返回具体结果，由组织者重新组织。

简单知识问答可以由宿主建立一个回答节点，Worker直接回答并交付，不强制增加前后两次组织请求。它仍然使用相同的节点输入/输出机制；需要进一步安排工作时再进入组织形态。

最重要的语义：**节点执行结束、结果符合预期、用户整体目标达成，是三件不同的事。**

## 2. 当前实现需要改变的地方

| 位置 | 当前行为 | 改造要求 |
| --- | --- | --- |
| `src/work_scheduler.rs::return_work` | blocked、need_split、upstream_problem 返回后常保留未完成状态 | 明确返回结束本次节点调用；具体问题进入返回值，组织者接着安排任务 |
| `gate / close_if_satisfied` | HTTP 2xx、检查退出码 0 与节点能否结束绑定 | 保留客观成功判定，同时允许任务以真实的负面结果结束 |
| `src/work_executor.rs::advance` | 只有 scheduler.done 才调用 Flow complete_work | 所有有效的任务返回都封存当前调用及节点结果 |
| `src/work_organizer.rs` | 一个 organize_work 参数树包含 work/select/continue/revisit/finish/blocked、Flow 更新及旧契约迁移 | 改为少量明确的调度方法；程序生成 ID、更新节点及切换上下文 |
| `src/agent_service.rs::apply_organizer_decision` | 先校验 Flow 更新，再处理结束，错误常落入通用 decision 字段 | 从生产调度路径移除模型手工提交 Flow 状态的职责 |
| `organizer_input` 和宿主输入拼装 | 同一节点信息出现在多份目录、Flow、结论和工作索引 | 组织上下文只保留当前返回、精简执行路径和必要事实 |
| `src/flow_tree.rs` | AI 需要处理父节点聚合、叶子更新和 resume 等协议 | 调度器负责节点生成、结果提交、依赖连线和回溯废弃 |
| Worker/Organizer 提示词 | 把能力不足等结果描述为悬而未决的执行单元 | 输出当前任务的事实和限制，返回后退出该执行上下文 |

本计划替代旧文档中与以上语义冲突的条款。现有权限、原生执行工具、记事本、素材版本校验、浏览器上传绑定、截图归属及持久化能力继续复用。实施时同步更新 `docs/work_scheduler.md` 和旧实现要求的有效范围。

## 3. 简单的数据模型

### 3.1 节点只保留三个执行状态

```text
ready → running → done
```

`done` 表示这次调用已经返回，其结果不可再被普通调度改写。连接拒绝、HTTP 404、视觉能力不可用、需要拆分，都可以是结束调用后的结果。

返回需要拆分时，原节点记录“本次发现任务需要分解”及已得到的材料。新任务引用这个结果，逐个展开；不保留一个等待反复 resume 的旧执行包。树的分组关系可以保留，分组本身不要求旧 Worker再次执行才能聚合完成。

废弃属于历史有效性标记，不增加执行状态。暂停/取消属于用户控制信息；兼容旧界面时可映射显示，但不再让组织者维护一套额外生命周期。

### 3.2 输入与输出

建议复用并收敛现有 WorkOrder/WorkFrame，而非同时建立第二份任务状态库：

```text
TaskInput
  goal                 当前这件事的目标
  return_when          本次应返回什么结果，何时结束
  inputs               必要的上游输出或明确参数
  constraints          用户约束与范围
  material_refs        需要时可读取的材料位置
  execution_scope      必要的编辑目标、允许操作和检查要求

TaskReturn
  summary              当前任务实际得到什么
  data                 结构化结果
  material_refs        详细日志、源码、截图等材料引用
  limitations          未能完成的部分及原因
```

node_id、执行实例、版本、时间、真实工具操作和已验证事实由宿主补充。Worker 不填写节点状态，不伪造 tool receipt。数据有缺失必须明确表达，不能把“未知”写成 false 或成功。

宿主记录客观的条件达成情况，例如实际写入、编译是否通过、HTTP 状态、页面是否加载和图片是否收到。这些事实独立于节点的 done，不采用一个全局 success 布尔值替代所有业务判断。

首版不强制每种业务都定义一个复杂 JSON Schema。输出要求写清必要字段，宿主对已有结构化工具事实进行校验；后续按真实需求补充类型。

### 3.3 负面结果的示例

检查任务：检查字体接口当前能否访问，并返回实际结果。

```json
{
  "summary": "字体接口拒绝连接，未收到 HTTP 响应。",
  "data": {
    "url": "http://127.0.0.1:8080/api/fonts",
    "reachable": false,
    "http_status": null,
    "error_kind": "connection_refused"
  },
  "limitations": []
}
```

宿主将此检查节点置为 done，保存原始 sampled_at 和样本 ID。组织者可以据此安排定位原因。不得要求得到 200 才让“查明是否连通”这一任务结束。

任务若是“恢复字体服务并确认可用”，连接拒绝只能说明恢复目标尚未实现。执行器在允许范围内进行有限的实现/检查/修复；无法继续时返回实际做过什么及未达成条件，结束此次调用。不能把节点 done 展示成服务已经恢复。

检查工具调用成功、程序退出成功、业务预期满足分别记录。例如浏览器工具成功报告页面错误，仍然是有效的检查产出。

## 4. 把调度器变成组织者的简单工具

首版提供以下明确方法，名称可按现有命名规范调整：

### 4.1 `schedule_task`

参数主要是 goal、return_when、inputs、constraints，以及当前任务需要的 execution_scope/material_refs。

- 创建一个新的任务节点，默认属于当前用户目标；宿主分配节点和执行实例 ID。
- inputs 中的上游引用按实际 node/result ID 和指定字段解析；无引用的其他历史不进入 Worker。
- 调度器自动创建 Flow 节点和依赖连线，激活该节点，交给 Worker。
- 一次派发只创建一个实际任务，不接收整棵 Flow JSON，不要求组织者填写父子聚合状态。
- 同一组织调用重放时不得创建第二份任务。使用宿主调用 ID 实现幂等，而非要求模型自己生成可靠 ID。

### 4.2 `read_task_result`

按节点/执行实例读取已有输出及所需字段；原始材料通过现有记事本方法取回。默认组织上下文已经包含刚返回的结果，不能再为读取这份结果额外调用工具。

实现上优先复用现有 recall_nodes 和记事本检索，只增加统一的结果读取适配，不重新搭建另一套查询系统。

Flow 回顾可以分页/按节点检索，不默认携带整份历史树和所有操作日志。

### 4.3 `finish_request`

参数为非空 summary，以及整体目标是否已达成和未解决部分。结束正常交付和受阻交付使用同一个明确入口。

- 校验实际事实，不允许把缺图像的验收说成画面通过。
- 不要求模型提交 root.node_result、current_node_id 或手工聚合子节点。
- 子节点全部返回不等于用户目标已经达成；组织者根据目标和产出形成最终答复，宿主检查已有硬性事实。
- 受阻交付保留真实进展及限制，不因“没有全部实现”自动变为调度协议失败。

### 4.4 `revisit_task`

参数为 target_node_id 和具体回溯原因。需要时带新的任务范围。

- 保留旧调用的原始结果；为目标节点创建新的执行版本。
- 按用户既有要求，目标节点之后的旧下游任务全部废弃，在 Flow 中保留为灰色。
- 取消旧下游仍在运行的调用，旧版本晚到的工具结果、Observer 建议不得进入新路径。
- 从回溯目标重新组织后续任务。Worker 不同时修复上游并继续旧下游。
- 不自动撤销用户文件修改。文件改动作为事实保留，回滚仍走已有明确授权的工具。

每次组织阶段只提交一个改变调度的工具调用。历史查询可以按需进行，但不为重复解释或空的“准备开始”继续调用模型。

**退出生产路径的旧字段：** 模型手工 Flow plan/node_updates/node_result、普通节点 resume、preserve_current、父节点完成聚合、批量 select/continue 组合。兼容旧快照的转换保留在宿主边界，不再全部塞进模型工具说明。

## 5. 执行循环与持久化

可按生成器式调用理解：

```text
while 用户目标尚未结束:
    decision = AI组织(最终目标, 当前返回, 精简Flow路径, 相关约束)
    if decision 是最终交付:
        保存答复并结束
    elif decision 是回溯:
        调度器废弃旧下游，切换到新的目标调用
    else:
        task = 调度器创建当前任务(decision)
        result = 执行器运行Worker(task.input)
        调度器封存(task, result)
        当前返回 = result
```

调度器工具触发任务后，组织阶段暂停。Worker 返回后，再发起下一次组织模型调用。无需让 HTTP 请求在后台 Worker 执行期间一直挂起，也不在“派发已接受”后再额外调用组织者确认一次。

如果以模型 tool call 形式交接，可在下一次组织输入中保留最近一次 schedule_task 与对应 TaskReturn 的成对消息，其余组织历史存档。当前结果只传一份，避免同时出现在 tool result、current_result 和多个 handoff 里。

节点结果、状态变化、调度指针与 Flow 事件在同一 SQLite 事务提交；节点返回按执行实例唯一记录。复用现有 Observer 的事务事件接入，不新增独立数据库。

宿主重启后，已返回节点仍是历史事实；实时资源状态标为需确认。对执行中且是否产生副作用不明确的任务，先恢复实际记录，不能自动重放启动、写入或上传操作。

## 6. 上下文视野

### 6.1 组织形态

默认只提供：

1. 用户当前总目标、范围和最终交付要求。
2. 刚结束任务的一份输出。
3. 当前有效执行路径：每节点 ID、目标、结果摘要及引用。
4. 与下步决策有关的当前事实、能力和 Observer 建议。

同一节点只保留一份索引。完整历史 Flow、所有 source/material 正文、全局 findings、长日志和旧迁移规则不自动注入。

组织者使用同一模型和用户推理配置。先通过减少无关输入和多余纠错减少耗时，不额外增加一个组织模型配置项。

### 6.2 执行形态

只提供当前任务、必要上下游输出、当前材料选择与本节点工具记录。上节点具体如何寻找和试错留在该节点与记事本中。

切换节点退出当前调用上下文，材料仍长期保存。真正实施时按文件及行范围读取需要的源码。组织者不能把整套历史目录复制给下一 Worker。

### 6.3 事实与新旧状态

- 宿主将结构化工具结果自动保存为可交付事实；Worker 不必再次汇报才能保住材料。
- 每个事实有来源和时间；代码、进程、浏览器资源有对应版本/归属。新事实替代当前结论，旧事实留为历史。
- “节点已结束”与“该节点观察到的资源此刻仍有效”明确分开。不能将上轮 running=true 描述为本轮服务已启动。
- 事实过期不会重新打开旧节点。只有新任务确实需要当前状态时才安排新的检查。
- 源码写入和检查结果按当前文件版本绑定；观察任务的 HTTP 404/拒绝连接不会被篡改成通过。

## 7. 重复与异常处理

### 7.1 减少重复检查

调度器在新任务派发及工具执行前检查相同目标、参数、已交付结果及相关输入版本。

- 已有结果能回答当前问题时，直接提供结果；不让 Worker为了恢复材料重新探测。
- “再次确认”或改写 observation_purpose 本身不构成事实变化。
- 实际启动/停止、代码或页面变化、外部资源需要新的时效观测、明确的有界重试，可支持新检查。
- 外部资源无法保证永远稳定，不能把所有重复 URL 永久禁止；宿主用真实有效性与当前任务需求决定复用。
- 精简记录复用原因、使用的样本及时间，不制造新的采样时间。

### 7.2 正常修复与需要交接的区别

一个“实现并检查”的节点可以在自身范围内进行有限的实现→检查→修复→检查。一次编译失败不强制新增一个节点。

当本次明确结论已形成、能力缺失、出现外部依赖、范围需要扩大或停滞时，结束本次调用并返回实际问题。组织者建立下一任务；不靠 continue 重复宣称要动手。

### 7.3 协议错误与 API 错误

- 工具 schema、宿主校验和提示词使用同一契约来源；结束方法的 summary 在工具声明中必填。
- 错误返回准确 rule_id、字段路径、原因及最小有效示例。不要依赖报错字符串包含某个词再猜字段。
- 协议修正次数有明确上限，错误识别排除总结文字等无关字段；不允许改写一句话就绕过重复检测。
- API 超时记录为请求失败，重试保持同一任务实例及已保存结果，不能生成重复节点。
- 协议仍无法恢复时，由宿主直接输出已有进展和调度错误；不为了生成这份错误报告继续循环请求 AI。

### 7.4 能力不足和交付资源

视觉能力未知/不可用时，节点返回“已截图但未能检查图像”。宿主保留截图及实际输入模式，组织者可以选择可用方式或结束受阻交付，不能宣称画面通过。

派发任务前提供真实模型路由的图像输入能力。组织者在安排验收前就知道该限制；截图若是用户要求的交付仍可执行，不能直到最后才发现没有可用的图像检查能力。

已完成的可见页面和服务不因随后调度错误自动销毁。用户要求保留窗口时，按交付要求保留；用户关闭、明确替换或已有资源管理规则负责后续清理。

## 8. Observer

Observer 消费同一份宿主节点输入、关键执行事实、任务返回和组织者新派发的目标，能够发现：

- 组织者根据过时状态安排了错误的下一步。
- Worker已有足够结果仍重复查询，或者实际修改没有发生。
- 下一任务遗漏了必要上游信息，或与总目标无关。
- 检查结束被误当成业务成功，或截图存在被误当成画面通过。

Observer 不接管 Flow 状态，不成为交接审批步骤。建议进入下一次正常组织输入；节点执行期间涉及当前问题的建议可以进入 Worker 的当前输入，不增加专门回执轮。建议的消费记录由宿主记录。

节点结束的复盘复用当前输入/输出和已有观测，不强制每个节点再等待一次 Observer 模型调用。请求结束后保存已有复盘与知识，不能延长前台运行等待新审查。

## 9. Flow 与调试界面

- 根节点展示用户总目标；执行节点由调度器自动添加，并显示实际输入、任务目的、返回条件和结果摘要。
- 执行状态与业务结果分别显示。例如“执行结束 · 接口连接拒绝”，不能统一用绿色“成功”掩盖负面结果。
- 连线展示下一步/输入依赖；记录组织者为何根据上一返回安排当前任务。
- 详细工具过程、源码、截图、历史结果按节点展开。调试模式显示组织/执行/观察的实际请求及其来源。
- 回溯保留旧下游灰色节点，新调用记录新的执行版本和路径，不将 AB 的原始上下文合并。
- 兼容旧事件与旧卡片；新运行只从宿主事件生成节点，不依赖模型的 flow/node_state 调用。

## 10. 分阶段实施

### 第一阶段：统一返回语义

修改 `work_scheduler.rs`、`work_executor.rs` 和 `flow_tree.rs`：任务返回即结束当前调用；保留真实成功条件及限制；结果与节点状态一次提交。

交付：连接拒绝、HTTP 404、视觉不可用都可以形成 sealed TaskReturn，进入组织阶段；不能伪造业务成功。先解决负面结果无法交接的问题。

### 第二阶段：简化组织接口与主循环

修改 `work_organizer.rs`、`agent_service.rs`：接入调度工具，宿主生成节点，移除模型手工状态更新和父节点聚合协议。统一普通结束与受阻交付入口。

交付：任务返回→组织思考→下一任务；非法叶子更新和缺 summary 的旧收尾路径退出生产调用链。

### 第三阶段：输入输出与记事本

修改 `organizer_input / worker_input`、宿主输入拼装和 `worker_work_state.rs`，复用 `task_notebook`：一份当前返回、一个精简路径索引，按需选材料；跨节点事实携带有效性。

交付：检查过的结果在下一任务中直接可用；不再将历史启动记录视为当前运行证明。先记录请求体分项大小，再确定裁剪阈值，避免用随意字符上限裁掉关键返回。

### 第四阶段：动态 Flow、回溯与 Observer

更新 `flow_tree.rs`、前端 `model.ts / TaskNode.tsx / FlowView.tsx`、`observer_service.rs`：显示节点执行和结果，贯通新派发与复盘事件，保留灰色废弃路径。

交付：已有路径可回顾，必要时读取原始材料；回溯后旧下游不再参与调度和上下文。

## 11. 启动 PPT 项目的期望路径

这是一条示例路径，组织者必须根据实际返回动态选择，不能写死为必经流程：

```text
确认已知地址的服务状态
  返回：编辑器/字体服务不可达
    → 按需定位缺失服务的启动方式
      返回：已有 dev 脚本及服务关系
        → 启动必要服务
          返回：进程与实际就绪结果
            → 打开可见编辑器并上传真实 PPT
              返回：上传和应用加载结果，8 页
                → 检查页面、字体请求和截图
                  返回：实际发现；图像输入缺失时明确限制
                    → 完成交付或说明剩余条件
```

如果已知脚本和端点，无需再做发现。如果服务已正常，无需启动。如果上游已有当前加载确认，后续直接消费。需要重新检查时必须对应实际状态变化或新的验收问题。

## 12. 验收要求

| 场景 | 预期行为 |
| --- | --- |
| 字体探测拒绝连接 | 检查节点 done，返回真实负面事实；下一任务按需诊断/恢复 |
| HTTP 404 | 节点可返回；404 不算 2xx，也不继续在检查节点里等到 200 |
| 启动操作后检查字体 | 使用新的采样；可达结果与旧拒绝连接有清楚的时间/来源 |
| 实现并编译成功 | 宿主记录真实写入和当前版本检查通过，自动返回，不增加收尾确认轮 |
| 编译失败但可在范围内修复 | 当前 Worker进行有限修复；无法继续时返回真实结果及未达成项 |
| 有结果但服务/页面已变化 | 历史节点仍 done；新任务取得当前状态，旧样本不冒充新结果 |
| 视觉能力不可用 | 已捕获截图与无法验收分别记录；正常受阻交付，无四轮非法收尾 |
| 已有当前空进程清单 | 不为“再确认”强制重取；有具体状态变化或新时效需求才新查 |
| 调度调用重放/宿主重启 | 不重复创建节点、启动服务或上传文件；不明确副作用先恢复事实 |
| 回溯到 A | 旧 A 输出保留，A 新执行版本开始；旧下游灰色废弃，晚到结果隔离 |
| 简单知识问答 | 一个回答任务节点，回答返回即可交付；不查询源码、不生成通用研究/编码/验证链 |
| 组织请求协议出错 | 精确字段反馈、有界纠错，无法恢复则宿主交付已有结果和原因 |
| Observer发现重复操作 | 建议进入当前执行/下一组织调用；无额外审批或回执轮 |
| 后续调度失败但页面已打开 | 保留用户要求交付的窗口和材料 |

验收分别统计节点数、Worker/组织/Observer模型调用数、工具实际执行与复用次数、重复操作原因和各阶段耗时。不得只用一个笼统 step 数评价过程。

## 13. 首版范围

首版串行执行，一个活动任务、逐个添加节点；保留现有树分组、依赖及回溯能力。不增加可配置的组织者、不引入多 Worker并行或复杂事务回滚框架。

优先打通负面结果返回、动态派发与稳定交付，再优化上下文和界面。改造重点在当前执行循环与契约，原生工具和材料存储不整体重写。
