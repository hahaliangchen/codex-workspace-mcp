# Observer 关注组织者与当前节点：实施计划

日期：2026-10-05。项目：`D:\enterpriseProject\codex-workspace-mcp`。

## 一、目标与职责

观察者审视组织者的任务安排和当前节点的实际推进：这一步为什么需要做、输入是否够用、产出是否推动用户目标、走到这里是否偏离方向，以及路径能否缩短。

| 角色 | 职责 |
| --- | --- |
| Organizer | 理解需求、派发当前工作、消费交付和观察建议、决定下一节点或回溯 |
| Worker | 独立完成当前节点的实现、检查、普通修复和交付 |
| Observer | 评估组织决策、当前节点及通往此处的浓缩路径，提出纠偏意见、沉淀经验 |
| Scheduler / Executor | 校验决策、维护版本和简单状态、执行工作、封存交付 |

Observer 的主要建议接收者改为 Organizer。Worker 接收组织者落实后的当前任务输入；主动查询历史信息仍可保留 consult_observer。Worker 不需要为阅读或回复观察建议增加独立模型轮。

沿用 ready/running/done。复盘状态和建议处理记录是旁路元数据，不增加执行状态机，不新增组织者模型配置。

## 三、观察者的上下文

### 3.1 全局部分只保留浓缩视野

包含当前用户目标、共同约束、有效计划概览、当前执行指针、选定上游交付摘要、相关已完成节点的复盘摘要。废弃路径作为按需历史参考，不作为当前任务要求。

### 3.2 当前节点部分

包含组织者本次决策及理由、节点目标和完成条件、已解析输入交付、材料位置、Worker 的简短目的汇报、实际工具活动摘要，以及当前交付/阻碍。

普通编译失败只作为“Worker 正在本节点修复”的事实；只有导致反复停滞、扩大范围或暴露上游问题时才进入路径评估。Observer 不重查源码、运行编译或代写代码。

### 3.3 输入预算

初始建议设为约 12,000 字符总预算，按字段裁剪：目标与当前决策优先，其次当前结果和关键活动，再保留至多 6 条相关路径摘要、3 条相关记忆。不默认加载完整聊天、旧工具正文或整个源码工作集。

预算是上下文打包参数，不是 Notebook 存储容量；完整原始记录仍可在调试界面查看。后续通过实际请求长度调整预算，不能以截断当前目标和交付来满足上限。

## 四、输入输出契约

以下为概念结构，名称按现有代码习惯调整。

```text
ObservationInput
  identity: task_id, request_id, node_id, work_id, revision, plan_revision
  review_id, source_event_id, organizer_decision_id
  stage: assignment | progress | handoff
  request: 当前目标、边界、约束
  organizer_decision: action、reason、派发/选择/回溯内容
  path_summary: 相关上游交付和既有复盘摘要
  current_node: 目标、完成条件、已解析输入、材料位置
  activity_summary: 工具次数、新信息、重复读取、实际修改、检查/阻碍摘要
  delivery: 本实例交付；派发阶段可为空

ObservationReview
  同一 identity、review_id、source_event_id、stage
  assessment: on_track | needs_adjustment | uncertain
  summary: 一句话判断
  findings: 最多 3 条，包含原因及已有事实/事件引用
  recommendations: 最多 3 条，可指出对象和建议调整
  reusable_lessons: 可选的经验候选
```

assessment 表示观察判断，不改变节点完成状态。建议可以是继续既定路线、缩小任务、复用已有交付、调整次序、拆分问题或考虑回溯。程序不得直接执行模型返回的建议。

信息不足时返回 uncertain，说明欠缺的具体事实；不能自动要求 Worker 再查全部文件。没有实质建议时 recommendations 为空。

## 五、节点复盘时机

| 阶段 | 可靠触发点 | 核心问题 |
| --- | --- | --- |
| assignment | Organizer 决策校验并提交、实例身份确定后 | 这一步是否必要？顺序与范围是否合理？Worker 是否可以直接行动？ |
| progress | 出现实质异常、重复读取、无进展、目标/依赖变化 | 当前路线是否偏离？已有信息是否足够？是否需要组织者调整？ |
| handoff | 节点 completed、blocked、need_split 或 upstream_problem 交付封存后 | 当前节点交付了什么？到达这里的路径是否合理？下一步应消费什么？ |

每个节点必须建立交付复盘记录。简短知识回答可将派发与交付合并为一次观察，不为一个直接答案固定安排两次 Observer 请求。

重试中的普通检查失败不产生节点交付事件。只读调查、实现、检查是 Worker 当前节点内部动作，Observer 不为每个工具调用建立复盘。

优先处理节点交付；同一节点尚未开始的派发观察可并入交付输入。进度请求按新事实或相同问题的有效变化去重，沿用现有节流能力。

## 六、异步机制与结束规则

### 6.1 边界事件不能只依靠 watch

watch 只保留最新值，快节点可能让 assignment/handoff 被后续 activity 覆盖。因此：

- 派发与交付在提交快照时写入明确的观察事件或待处理记录；以 request/work/revision/stage/source_event 身份去重。
- 观察循环通过有界通知通道唤醒，并从持久记录读取边界事项；通知合并或队列已满时，记录仍在。
- 高频 progress 保留最新快照；同一实例的旧进度可合并。
- 首版每个会话最多一个 Observer 模型调用在进行中，避免并发成本和重复意见。

复用现有 SQLite 事件及 execution/commit，不引入复杂任务平台。关键提交保证调度器、树和观察事项指向同一执行版本；临时通知不是唯一事实来源。

### 6.2 不把节点复盘变成审批

Worker 与 Organizer 继续推进。组织者在下一次正常交接时消费已到达的建议；当前节点发生实质性偏离时，可沿用已有停滞/交接路径通知组织者，并去重，避免每轮增加一次组织调用。

观察耗时或失败不会阻止节点完成、调用下一节点或回答用户。强制动作仍来自人类指令和已有程序权限规则。

### 6.3 避免请求结束后继续长时间复盘

节点复盘与执行并行积累；最终路径总结使用已有复盘、实际计数与交付生成，不再另起完整历史的长模型循环。

请求结束或取消时停止新观察调用。尚未完成的观察记录明确标记超时、取消或未完成，保留事实快照；不得展示成“已经检查，无问题”。正在执行的 Observer 调用可取消，结果晚到只进入原版本历史。

“每个节点有复盘记录”不等于任意时间限制下每个节点的 AI 判断都一定完成。界面应区分已评估与未评估，执行不等待补齐。恢复同一未完成请求时，可处理仍有效的必要边界记录；取消目标和已结束请求不自动恢复观察工作。

## 七、建议由组织者处理

1. Observer 写入具有执行身份的 review/advice。
2. Organizer 输入包含当前仍适用、尚未处理的建议与当前交付。
3. Organizer 在同一次决策中返回 accepted/adjusted/declined/resolved 和理由。
4. 程序记录建议落实到的 decision_id、工作包、字段或回溯事件。
5. Worker 下一轮收到已落实的输入、约束或节点安排。

接受意见应有具体落实内容；无需新增“我已读建议、准备行动”的 Worker 回合。意见处理也不重置无进展计数。

Worker 的 respond_observer 可为旧会话兼容保留，但从默认提示词和日常任务路径中移除强制回执要求。consult_observer 保留为可选历史查询；回答应是当前任务相关的精炼历史，而不是强制触发路线审查。

## 八、版本与回溯规则

- 所有输入、观察结果、建议和回执绑定 request_id/work_id/revision/plan_revision。
- request_action=replace 时旧意见归档；观察会话的目标和记忆缓存也更新，不能只换 request_id 而保留旧 user_request。
- 已废弃实例和被替代版本的结果只写历史，不进入当前 pending，不改变新实例。
- 同请求旧计划建议是否适用于新计划，由组织者显式重新采用；不由程序把版本号改成当前值。
- 同一节点实例的交付复盘晚到时，仍挂回原实例详情。若它发现影响下游的问题，以单独的当前计划建议通知 Organizer，由 Organizer 判断是否回溯。
- Observer 不重新打开 done 节点；回溯后由 Scheduler 创建新实例，旧下游仍灰色保留。
- 问题去重至少包含请求、实例、版本和 issue_key；相同术语不能让 A 的意见覆盖 B 的意见。

## 九、经验记忆

复盘可提出少量经验候选，例如“此类编辑先定位来源映射即可实施”“页面可达不足以证明示例加载”。事实和经验分开保存：

- 项目事实带已有文件/符号位置、版本或时间、适用范围；未经确认的内容保留不确定标记。
- 路径经验带适用场景、推荐起点、可省略步骤和例外条件。
- 原始建议、失败尝试和未解决问题留在节点历史；不能自动转换成下一请求待办。
- 重复经验合并；冲突或已替代的事实留历史，当前检索只投影有效结论。
- Worker 下一任务可通过现有记忆/Notebook 查询按需获取，不为写记忆另加工作轮。

复用 memory.rs、已有 retrospective 的结构和 known_read_targets 校验。符号描述只根据执行中已经得到的材料写入，不安排 Observer 重新调查源码。

## 十、Flow 与上下文调试

当前节点详情新增“决策与路径复盘”：

- 组织者派发理由及输入/输出摘要。
- 派发观察、节点交付复盘的结论，及未评估/超时标记。
- 哪些步骤可省略、是否偏离目标、是否需要上游修复。
- 组织者对建议的处理和实际调整。
- 节点版本、建议来源、回溯关系和经验记录。

全局条展示当前观察对象和简短路径判断，不把每条普通建议长成任务节点。只有组织者真正安排了修复/回溯工作，才改变执行 Flow。

调试模式按 actor=observer、review_id 和完整实例身份展示请求及结果。废弃节点仍可查看原复盘；复盘迟到不能改变当前高亮。

## 十二、验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| Observer 关闭 | Organizer + Worker 可独立完成，交付与结束不依赖观察意见 |
| 简单技术问答 | 一个执行节点、至多一次合并观察；无项目查询和回执空转 |
| 正常 A → B → C | 各节点有交付复盘记录，Observer 获得当前决策和选定上游摘要 |
| A 完成后 B 的输入足够 | 建议复用 A 交付；Worker 不因复盘重复读 A 源码 |
| 普通编译失败后修复 | Worker 在同实例继续，Observer 不审查语法或批准检查 |
| 重复查询/无实际修改 | Observer 指出信息是否够用和组织安排问题；Organizer 有具体处理，调用次数有界 |
| C 发现 A 上游问题 | 建议绑定 A 的交付版本，Organizer 决定 revisit，旧下游灰色保留 |
| 节点连续快速结束 | 派发/交付事项不被 activity 的 watch 快照覆盖；复盘状态可解释 |
| Observer 超时或请求失败 | 执行继续，显示未评估/超时，无等待审批或额外确认轮 |
| 新目标替换旧复杂目标 | 旧意见、旧观察缓存和晚到结果不进入新目标上下文 |
| 同节点 ID 重用或 revision 增加 | 旧复盘只属于旧 work 实例，不覆盖新输入、建议或高亮 |
| 交付重复事件/服务恢复 | 一个身份只登记一次复盘和经验记录，不重复派发任务 |
| 最终回答或取消 | 不另起长历史复盘；未完成观察显式标记，当前任务结束 |
| 记忆进入下一任务 | 只读取相关经验，取消目标的旧建议不成为当前待办 |

实施后至少提供正常路径、重复调查纠偏、目标替换和回溯四类实际记录；报告 Worker 工具/模型调用次数、Organizer/Observer 调用次数、观察耗时、建议处理和因观察新增的 Worker 回合数（应为 0）。

模拟测试须开启 Observer 覆盖身份与晚到边界，不能只用 observer_enabled=false 的脚本验证无旧上下文。真实模型验证用于评估意见质量与效率，前端事件重放/浏览器检查用于验证展示，两者不能互相替代。

## 十三、完成标准

Observer 的真实请求以当前组织决策和当前节点为中心；派发与交付复盘可靠记录；组织者处理建议并落实；Worker 可独立执行；旧版本意见不污染新计划；Flow 按实例显示；执行结束后没有额外长尾复盘。

交付报告逐项列出已完成、部分完成及未验证项，附代码位置和实际流程记录。仅改提示词、换角色名称或新增展示字段，不算完成本计划。
