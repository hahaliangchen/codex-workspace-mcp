# Agent 历史树目录与消息传递调整计划

日期：2026-10-12。

状态：待实现。本计划调整宿主装配上下文的方式，并为同一份对话历史增加目录索引。AI 决定哪些内容与当前任务相关、如何归类和读取；宿主保存原文、解析引用、维持顺序并检查容量。目录帮助定位原文，不能成为另一套执行事实或完成判定。

## 当前需要调整的实现

当前版本为 `3fbda85`。Observer 验收与自动补齐已经接通，以下两处仍由宿主决定接收者看到什么：

- `src/session_history.rs` 的 `organizer_view()` 按消息种类排除 Worker 工具调用、工具结果、中间说明及部分图片投递。即使上下文未超限，也会发生筛选。
- `src/agent_service.rs` 在 Observer 输入超限时调用 `src/observer_service.rs` 的 `acceptance_history()`，按预设种类选择部分原始消息，然后才进入 AI 的历史选择过程。

两处筛选最初用于减少上下文和验收等待，但“历史仍可查询”不能替代接收者对所需内容的自主选择。需要取消这类宿主预筛选，保留现有的 AI 历史读取与 `select_context` 能力，并解决选择过程反复展开材料的问题。

现有 `order_context_messages()` 的原始顺序恢复、来源传递、原图读取、实际请求保存和验收补齐继续使用。目录改造不改写既有消息和已保存的角色请求。

## AI 与宿主的职责

| 工作 | 负责方 |
| --- | --- |
| 判断当前有效要求、历史内容是否相关、是否需要补齐 | 对应角色 AI |
| 给历史段落起标题、写涉及要点、关联同一件事的多段对话 | AI |
| 决定读取哪些章节及原文，超窗后保留哪些引用 | 当前接收角色 AI |
| 保存原始消息及 AI 提交的目录项 | 宿主 |
| 将引用解析为原文，携带原执行者、轮次、调用和失败信息 | 宿主 |
| 同一会话按原始顺序装配，保留工具协议关联和原图内容 | 宿主 |
| 检查用户权限、引用是否存在、窗口是否超限 | 宿主 |

宿主不能依据消息种类、成功或失败、关键词、角色身份判断信息的重要性。技术检查失败时返回具体原因，不能替 AI 改选内容或写摘要。真实发送给某个角色的命令及必要协议仍须正确路由，不能把协议要求扩展为内容筛选规则。

## 历史树目录放在哪里

目录属于 Agent 的对话历史索引，存放在当前 Agent 工作区已有的 `.codex-workspace-mcp/codex_state.db` 中，与 `agent_tasks`、`agent_task_events` 共用存储位置和历史读取入口。具体路径沿用现有工作区定位方式，不硬编码某台机器的项目路径，不另建记忆服务。

第一版采用项目内会话目录、会话内主题章节两层。需要更细的章节时由 AI 增加子项，不要求每次工具调用都成为目录节点。一个主题可以引用多段不连续的原文，同一段也可以被不同主题引用；原文只保存一份。

目录项保存这些内容：

- 标题、涉及要点和父目录引用，由 AI 提供。
- 原文引用，明确所属会话和事件编号，支持多个范围或离散消息；长消息可引用切片位置。
- 创建及更新者的来源引用，表明谁在什么时候整理了这项目录。
- AI 明确给出的关联，例如补充、修正或替代哪项旧讨论。宿主不从措辞中推断这些关系。

执行者、轮次、调用编号、失败标志和图片来源仍以被引用的原始记录为准，不在目录中另建上传次数、业务状态或图片交付账本。

## 目录内容示例

以下为格式示意，不代表已生成的真实索引：

```text
会话：运行 PPT 编辑器并检查两页
├─ 服务与浏览器
│  涉及：已有服务、可见 Chrome、原连接及恢复失败
│  原文引用：同一会话中的有关消息
├─ 文档加载
│  涉及：上传调用、加载回执、页码及指定文件
│  原文引用：同一会话中的有关消息
├─ 两页检查
│  涉及：翻页、截图、实际图像输入、显示观察
│  原文引用：同一会话中的有关消息
└─ 验收与补齐
   涉及：当前要求、未确认项、验收结论和补齐结果
   原文引用：同一会话中的有关消息
```

目录简述可以说明讨论涉及哪些点，但“涉及图像输入”不能证明已经看到图片，“讨论重复上传”不能证明发生重复执行。结论核查要读取原文。后来出现修正时，由 AI 更新关联和说明，早期记录仍可定位。

## 消息传递与上下文装配

窗口内按原始顺序传递当前会话过程及真实交接，不按消息类型排除结果、说明、失败或能力限制。Worker 本次明确获得的命令和输入保持原样；需要历史时提供与 Organizer、Observer 相同的历史目录和原文读取入口，权限一致，来源一致。

256k 是最大视野，不是每次请求都要填满。已由 AI 选择的原文继续保留，后续新消息按顺序追加；宿主不能为了缩小输入，提前替角色判断新消息是否值得看。缺少信息时，角色可主动查目录并读取有关原文，不必等到窗口超限。

接近容量时，由当前接收角色结合最新用户要求及历史目录选择必要原文。宿主恢复 AI 选择的引用，按原会话顺序装配，并保留当前新消息和原生工具调用与返回的协议关系。不同会话的局部序号分别处理，不能直接混排为同一条时间线。

选择阶段不能先展开全部历史再让 AI 查一遍，也不能先按消息种类缩减历史。起步使用当前原始指令、最近原始消息、已有选择引用和 AI 编写的目录，提供未展开范围及按需读取入口。最近消息的可用范围只由顺序和容量决定，不由宿主判断内容重要性。目录过大时逐层或分页读取，由 AI 选择继续展开哪里。

长原文分段读取必须标明范围及剩余部分，不能静默截断或把“读取部分”标成“读取完整”。图片引用保留可读取的原图和实际交付信息；目录中的描述不替代像素。超过容量时，AI 决定需要哪些图及原文，宿主如实返回容量限制。

## 如何形成和使用目录

优先复用 Organizer 的任务安排、Worker 的原始交接和 Observer 的验收对话，让角色在已有调用中提交目录更新。不为每条消息增加一次总结请求，不要求 Worker 再写一份进度报告，也不因目录变化触发业务执行或验收。

第一版只增加目录读取和 AI 提交目录更新的方法，沿用 `read_session_history` 读取目录引用。支持一次选取多个章节并批量取原文，避免先逐章搜索、再逐条读取。宿主处理引用重叠时按同一来源关联，不能因文字相同就合并不同执行。

旧会话没有目录也能正常读取。AI 在确有需要时读取有关原文并补充索引，不启动后台模型遍历全部会话。目录未覆盖最新消息时，返回实际覆盖范围和未整理的新消息引用，不声称历史已经全部整理。

正常读取流程为：看目录，选相关章节，一次读取所需原文，再作判断。已经收到必要信息时可以直接继续工作，目录查询不是每轮必须走的仪式。

## 实施顺序

1. **修正宿主预筛选。** 去掉 Organizer 的消息种类排除和 Observer 的 `acceptance_history()` 预选分支；同步调整提示词、回归断言及 README。先验证接收者不会因消息种类丢失原文，不用扩大超时掩盖输入问题。
2. **增加共用目录存储与方法。** 在现有数据库增加目录项及原文引用，支持 AI 创建、更新、关联和读取。数据库升级不改既有历史；目录写入不能删除或改写正文。宿主只校验结构、引用和权限。
3. **接通按目录批量读取。** 三个角色使用同一入口，保留每段原文来源、切片范围、调用关联及图像信息。旧会话无目录时沿用原始查询，按需补建。
4. **接通 AI 的上下文选择。** 将目录加入现有 `context_rebuild` 选择过程，保持 AI 选择引用和宿主按序恢复。检查多次读取是否重复展开同一批正文，避免另一条路径重新出现宿主预筛选。
5. **完成回归和真实复验。** 先验证消息与目录引用，再运行正常 PPT 任务及原会话续聊。观察是否减少查询和等待，同时核对结果完整性。

第一版先实现存储、方法与上下文接入；聊天界面的目录树展示可在验证读取效果后补充，不作为模型可使用索引的前提。浏览器控制、图像数量限制和停滞检测属于另行讨论的现有规则，本计划不顺带修改。

## 验证场景与完成标准

| 场景 | 核对内容 |
| --- | --- |
| 窗口未超限 | 工具成功、失败、中间说明和能力限制不因种类被宿主排除；接收者保留原文和来源 |
| 超窗选择 | 被保留的业务原文能对应 AI 明确选择；宿主不按成功、失败或角色类型预选 |
| 一次上传、多次回执引用 | 目录定位实际调用和后续读取，原文只有一次上传，不把引用次数算成操作数 |
| 图片捕获与输入 | 目录可定位截图、选图和实际像素交付；没有新选图不被写成没有图像输入 |
| 多轮要求与修正 | 新旧要求保持原始顺序，修正关联由 AI 提交，宿主不判定哪条要求有效 |
| 跨章节、分页及切片 | 批量读取保留原顺序和来源，不混用会话局部序号，不因同文合并不同调用 |
| 缺目录、旧目录或错误引用 | 能读原始历史；明确覆盖范围和引用错误，不能静默遗漏最新消息或触发重做 |
| 重启与验收补齐 | 目录和历史一起恢复；补齐沿用原任务，已有成果和失败仍可查，目录更新不触发第二次验收 |

目录功能的完成依据是 AI 能通过主题定位并批量取得所需原文，三个角色读到相同来源记录，且消息选择权没有回到宿主。回归中要保存 AI 的选择调用和实际发送输入，证明内容来自这些选择。

真实测试沿用已有 PPT 任务：运行 `/home/goodtime/project/pptx-editor-engine`，在可见 Chrome 加载指定示例 PPTX，检查第 1、2 页并保存截图、读取诊断，保留服务与窗口，不修改业务源码或模型配置。续聊要求为“在刚才的页面上再检查一下第 1 页和第 2 页，保留窗口和服务”。其他系统使用实际项目路径。

比较旧查询和目录查询时使用同一份已保存历史、相同问题及模型配置，分别记录历史读取次数、目录读取次数、总模型请求次数、输入规模、等待时间、漏掉或误读的原始事实。目录生成与更新成本一并计入，不能只统计读取提速；真实 PPT 两轮的服务状态和模型等待不同，不能直接当作受控性能比较。
