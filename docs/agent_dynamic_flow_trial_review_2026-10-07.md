## 优先问题

### 1. 一轮汇报就强制交回组织者，截断尚未返回的任务

实际 Worker 请求 611、619、627、642、646、652（步骤 6、9、14、27、29、33）均只调用 `report_progress`。这些请求表述下一步操作，既未执行下一步，也未调用 `yield_work` 返回任务结果。宿主立即生成 `done=false, output=null` 的组织者交接。

对应实现：`src/work_scheduler.rs:1098` 的 `idle_rounds >= 1`。它将一次纯汇报视为需要组织者重新决策。组织者经常重新派单，从而把“员工汇报后继续执行”变成“汇报 → 换任务 → 再汇报”。这与一个节点完成后再回到调度器的约定不一致。

建议：正常轮次汇报不触发组织者；主要边界是明确 TaskReturn、真实阻塞、需要拆分或明确的持续停滞。停滞按实际新增信息/动作判断，不能每次报告都重派任务。

### 2. Observer 的实际输入丢掉已完成任务的结构化事实

启动节点的原始返回有两个 200 响应、采样时间、进程 ID 和受管进程观察。组织者请求 609 正确使用它安排上传。但 Observer 请求 610 的 `delivery` 只有摘要与 `exported_fields` 字段名，没有值；`http_observations` 不在实际请求中。其活动摘要也缺状态码、时间和进程结果。

Observer 因此提出 advice_11，称缺少服务就绪细节。组织者请求 613 改回服务检查，重复探测两个已确认服务。

对应实现：`src/observer_service.rs:63` 的 `pack` 未保留顶层 `http_observations`，`delivery` 只保留部分摘要字段；`compact` 在第 53 行按对象前 16 个键截断，不能保证保住有意义的字段。

建议：交付摘要必须包含明确结果、时间、必要的过程/接口状态与限制。按业务字段选择摘要；Observer 缺材料时读取已有返回，不应默认缺事实就让 Worker 重做操作。

### 3. 重派任务先废弃当前节点，导致其结果不能作为后续输入

事件 2003、2415、2426 的组织者依赖输入被拒绝。第一次引用当前任务的准确 work ID 也被拒绝；后两次先混用了 node ID 与 work ID，纠正为准确 work ID 后仍被拒绝。

根本条件是上一个任务没有返回，仍处于 running。`src/work_scheduler.rs:2306` 在调度新任务时先把当前未完成任务标记为 invalidated，再调用 `enqueue` 验证依赖。这时新任务若要承接当前工作，就会报 `has no active frame in plan`。这个错误提示没有直接说明“前一任务尚未返回，且正在被本次调度废弃”。

建议：未返回的当前任务不能默认为正常上游；继续当前工作、明确取消/回溯、已返回后派发下一步应有明确区别。正常 A → B 必须先封存 A 的返回，再校验 B 的输入，不应通过废弃 A 完成交接。

### 4. 当前上传回执从列表消失，旧失效回执反而引发重新上传

第一次实际上传事件 1923 成功，后续多次读取一直显示同一文稿 loaded、8 页。组织者重派时废弃 `_5_10`、`_5_16` 等未返回节点。请求 647 的 `process.browser_upload_availability` 只剩旧宿主的三个历史失效回执，当前成功上传不在列表中；当前结果为 null。

组织者将“历史回执因 browser_session_changed 不可用”误认为当前文稿必须重传，于步骤 30 再次打开页面，步骤 31 再次上传。此前并没有浏览器返回表明当前文稿丢失。重复打开会重置当前页面和导航诊断；此前 favicon 404 不再出现在新导航的诊断中。

建议：维护独立的当前页面/上传状态，并明确标注来源、时效和历史状态。不能因调度节点被废弃而丢掉仍有效的浏览器事实。摘要不足时先查已有返回或当前状态，不应直接重置已交付页面。

### 5. HTTP 去重校验制造错误往返，Worker 也仍误读时间线

最终共 13 次 `http_probe` 调用，其中 7 次被拒绝（事件 1600、1602、1804、1806、1964、1966、2657）。最初两个旧样本已有约 3 小时且宿主变更，任务明确要求获取当前状态，仍必须额外补 `reason` 才可采样。最后一次旧样本已约 12 分钟，仍报相同理由缺失。后续确有重复采样，去重不能一概放开。

步骤 8 的重探测理由声称前次样本在启动之前，实际启动进程时间为 08:42:46 UTC，前次成功样本为 08:42:59 UTC；模型仍误读了已有顺序。

建议：提供“上次结果 + 当前是否可复用 + 失效原因”的明确宿主状态。真实过期或输入变更后的合法观察不应靠一次失败才发现必须加理由；新鲜可用的结果应直接复用。保留结构化启动/探测顺序，避免模型重新推断时间关系。

### 6. 字体诊断工具不能提供它所承诺的正常 API 请求信息

Worker 连续读取 `browser_diagnostics`，仍拿不到实际字体 API 请求。源码 `src/browser_control.rs:232` 的资源过滤仅保留字体后缀/字体 initiator 或 HTTP >=400；`/api/fonts` 的正常 JSON 200 不满足此过滤。第 257/259 行 fetch/XHR 包装也主要记录错误，正常请求没有进入返回的事件列表。

因此返回空列表不能说明没有请求；多读几遍相同工具也不会补齐该证据。

建议：工具返回有范围说明的请求记录，可按 URL/资源类别查询成功、失败及时间，明确跨来源状态未知的情况。字体 API 健康与浏览器实际使用字体分开报告。能力缺失时返回明确限制，由组织者决定停止或改用已有工具能力。

### 7. 视觉能力未确定，仍反复分派必须看图的任务

组织者输入已声明 `visual_input.capability=unknown`、`fallback_available=false`，却多次下发视觉任务；甚至将“查看字体网络记录”放入 `visual_goal`。实际 `view_image` 结果和最终视觉返回为 `input_mode=not_received`，不是看图成功。

建议：区分截图捕获与模型看图，提前明确图像模型能力/备用路径；无法看图时直接交付截图及限制，避免继续派发相同不可完成动作。网络检查也不应自动成为视觉检查。

### 8. 浏览器控件定位与操作批量能力仍有缺口

按文本“下一页”点击失败一次（2058），改用 `#btn-next` 后成功。工具读取显示的控件标签与点击实际匹配规则需要一致。翻页动作、读取和等待多次分成单独模型往返；只点击了几次却先期待 `Slide 8 / 8`，随后仍逐页推进到 5/8。

建议：已有精确 selector 时直接使用；工具支持有界重复动作或针对明确目标页的导航，并返回操作后的当前状态，减少每个小点击都经一轮模型思考。判断最终页是否到达必须依据实际页码，不可从总页数推断。
