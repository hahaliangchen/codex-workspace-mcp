# 验收函数的串行闭环与后续优化

记录日期：2026-10-27。本文件用于交接当前讨论、真实测试结果和下一步方向；方案部分尚未作为新实现或已验证示例发布。

## 目标与范围

主流程继续负责完整任务、依赖和分工。验收不需要为了并行而启动子 Agent：先让单个验收虚函数在自己的上下文里按实际结果一步步工作，完成检查、授权范围内的处理与复查后返回。这个原则只用于承担相应职责的函数，不把所有虚函数或所有业务都强制改成同一种流程。只负责检查的函数可以返回问题，由调用方决定后续处理；只有当前职责和授权允许时才修改。

虚函数的参数可直接接收主函数已经取得的真实值，不需要因为进入函数而重新读取原资料。检查外部资源的当前状态、修改后的状态或实际交付物时，仍应按需要读回。执行者能在同一函数上下文里依次调用工具、观察结果、分析、处理和复查；简单工作不必再写源码，复杂且确有明确步骤时可用 `define_task_body` 补写当前函数，保持名称、参数数量和返回契约。

## 当前已经实现的边界

- 普通函数在宿主 Runtime 函数帧中执行；显式 `@virtual` 调用进入 AI 任务上下文。函数内多次工具调用是步骤，不会因此启动多个并发 Agent。
- 主流程只有在授权时通过 `fork` 启动子 Agent，`join` 收集结果；隔离 Git 工作区的整合由主流程按实际句柄检查并合并。验收任务本身不需要再启动子 Agent。
- 普通函数可读取调用位置可见的上层变量快照；具体规则见 [流程语言手册](agent-program.md)。未引用的上层变量只展示索引，AI 可用 `host.read_scope` 按需读取；不会将完整父作用域正文自动装入每个模型请求。虚函数只有自然语言注释，宿主不能可靠地从文字猜测变量引用；明确需要的值可以通过参数交接。
- 当前 AI 函数补写的函数体出现未捕获错误时，宿主记录错误并把控制权交回当前函数；可基于回执和保存的变量继续处理或报告失败。普通主流程的未捕获错误仍停止。不能自动重放已完成或结果未知的外部操作。
- 可确定的检查应由流程代码或工具执行；需要理解的判断由 AI 基于实际证据处理。函数契约中可确定的输入与返回关系由调用方按该任务契约核对。通用宿主不预设业务字段、产物类型、验收结果或统一修复流程。

## 真实五页测试：先做简单版本

2026-10-27 使用 `gpt-6-luna`，用户需求为生成五页并使用主 Agent 与一个子 Agent；特别要求验收时由同一个 AI 虚函数在自己的上下文逐步检查、按需处理和复查。没有全局改写主流程的执行方式，没有故障注入，运行中没有补充提示或人工修改产物。

实际流程由模型编写：[原始流程代码](examples/serial-acceptance-2026-10-27/main.js)。主流程完成分工、生成、合并和读回后，调用一个 `reviewAll` 虚函数。验收函数在同一个任务上下文里逐页读取五份文件、按需读取上层变量，然后返回检查结果。它报告未发现需要修复的问题，因此**本轮没有真实触发修复和修复后复查，不能据此认定自愈通过**。

五份原始产物已随源码保存，便于其他机器查看：[第 1 页](examples/serial-acceptance-2026-10-27/agent-design-zh/01-overview.html)、[第 2 页](examples/serial-acceptance-2026-10-27/agent-design-zh/02-program.html)、[第 3 页](examples/serial-acceptance-2026-10-27/agent-design-zh/03-tools.html)、[第 4 页](examples/serial-acceptance-2026-10-27/agent-design-zh/04-agents.html)、[第 5 页](examples/serial-acceptance-2026-10-27/agent-design-zh/05-quality.html)。它们是这次运行的输出，不是新的通用模板。

实测结果：5 个 HTML 文件存在，子分支已检查和合并；独立的本地链接检查没有发现断链，源文档未改动。AI 对文本和结构的检查返回通过，但未进行浏览器渲染或视觉验收，不能把这些结果等同于全面质量保证。总耗时约 292.53 秒，19 次模型请求，记录到输入约 1,370,736 token、输出约 30,388 token；单次输入峰值 134,409 token，发生在 `reviewAll`。实际发生 13 次文件读取、3 次 `read_scope`；这些是本轮现象，不代表所有任务都会如此。

本轮没有发现需要修复的问题，也未验证生成的流程能自动处理任何指定故障。之前另一轮注入样式链接错误，AI 发现并修复了该链接，但其余页面仍有断链和其他问题，整站验收失败；不能把局部修复成功说成整体验收通过。更早一次简单需求运行被人工停止，因为模型把检查与修复拆成了两个虚函数，不符合随后明确的测试目标；未将该次结果当作成功。

## 下一步：从单链向具体串行方法演进

先复现简单版本，再观察实际验收步骤和工具回执。稳定、可确定的步骤可以实现为当前验收函数调用的普通方法，例如顺序读取、循环、收集结果和契约核对；已知次数的重复工作可以用循环。需要智能判断的具体职责仍由 AI 完成。方法按依赖串行调用，不为验收另开多 Agent；如果调用虚函数会产生 AI 任务上下文，属于串行调用，不能误称是完全没有额外模型请求。

演进的目的是减少不必要的重复材料、上下文增长和调度，同时不预设某种业务的字段或把自由处理锁死。需要对真实工作量和数据流作取舍：把实际需要的值交给相应步骤，函数完成后释放局部工作上下文；不要为了降低 token 静默丢弃当前检查所需证据。普通函数无法代替语义判断，程序返回、工具成功和模型声称通过也不能代替业务验收。

建议下一次实际测试明确记录：提交的原始流程代码、各调用的输入与输出、同一验收函数中的工具顺序、是否触发真实修复及复查、模型请求次数、输入峰值、整体耗时、文件和链接检查，以及未做的视觉检查。要验证修复能力，可以在隔离测试中安排可审计的受控故障，不向执行中的 Agent 揭示故障内容；分别报告是否发现、是否修复、是否复检和最终是否整体通过。不要为了让测试成功人工改写其流程或产物。

原始运行目录 `runs/` 包含隔离 Git 工作区、数据库与模型请求日志，体积较大且可能包含敏感上下文，未提交远程。上面的五页和流程代码是专门挑出的可查看产物；不能把它们当成完整日志或请求上下文。
