# 组织者、调度器、执行器与 Flow：实施要求

日期：2026-10-05。项目：`D:\enterpriseProject\codex-workspace-mcp`。

本文用于交给实施 AI，定义必须交付的行为和验收标准。配套方案见 [实现计划](organizer_flow_execution_plan_2026-10-05.md)。回溯规则以用户最新要求为准：回到目标节点后，旧下游全部废弃，但继续在 Flow 中灰色显示。

本次只编写要求文档，未实施代码改造、运行测试或重启服务。

## 一、目标

把用户需求组织为可动态调整的任务序列 A → B → C → D。每个任务是一个逻辑进程，有自己的上下文、材料选择和执行结果。Worker 是该进程内部的工作执行者，每轮模型调用相当于一次局部方法调用。

组织者接收当前进程的交付，控制调度器决定下一步；调度器维护任务和执行指针，驱动执行器；执行器通过 next() 推进当前任务。

执行 B 时，只知道 A 已经交付什么及 B 所需的具体值，不默认关注 A 的内部过程。状态保持简单，沿用 ready/running/done，普通检查失败继续在同一进程内修复。

## 三、职责边界

| 组件 | 必须承担的职责 |
| --- | --- |
| Organizer，AI | 规划、派发、接收交付、调整未执行任务、决定回溯和结束；使用浓缩的全局上下文 |
| Scheduler，程序 | 校验并提交决策，创建任务进程，维护有效计划、依赖和当前指针，驱动 Executor |
| Executor，程序 | next() 执行当前进程的一轮工作，调用 Worker 和已有工具，记录结果，返回继续、交接或 done |
| TaskProcess，逻辑任务进程 | 保存独立的目标、输入、局部过程、材料选择、执行事实和输出 |
| Worker，AI | 根据当前任务直接做事，在本任务内完成实现、检查和普通修复 |
| Observer，AI | 持续观察进度和状态，提供相关建议、历史信息和经验记忆 |

进程可用现有 WorkFrame 和 Rust 异步逻辑实现，不要求操作系统进程或每节点独立模型配置。首版只有一个当前 Worker 执行进程；并发不属于本次必须交付的范围。

## 四、必须实现的要求

### R01：任务身份、执行版本与计划版本

- 稳定 node_id 表示任务节点；revision 表示该节点的执行版本；work_id 表示执行实例。
- plan_revision 表示有效计划版本。回溯时递增，用于区分废弃计划和重新规划后的任务。
- 一个执行版本的输出封存后保留，后续版本不能覆盖旧记录。
- 回溯事件记录唯一 ID、来源节点、目标节点、对应版本、原因、时间及作废任务列表。
- 执行、交接、请求、工具结果有足够的身份信息归属到正确实例。旧实例晚到结果不能推进当前新实例。
- 父节点表达总目标或子目标的归属；它不是与叶子同时执行的第二个 Worker。

状态仍用 ready/running/done。阻碍和需拆分作为交接结果，废弃作为计划归属标记。UI 可显示“已废弃”，无需新增一套复杂生命周期。

### R02：真实的单进程执行器

建议新增 `src/work_executor.rs`，从现有大循环逐段提取并复用工具实现。

必须能定位到类似下列接口，名称可按项目习惯调整：

```text
Scheduler.apply(decision)        校验并落实组织者决策
Scheduler.current_process()     取得唯一当前任务进程
Executor.next(process, runtime)  执行当前进程的一轮模型/工具工作
Scheduler.accept(tick)           归档结果并处理交接
Organizer.decide(snapshot)      根据交付决定下一步
```

- next() 应承担实际执行推进，不能只是读取 scheduler.done 的空包装。
- 普通 tick 的 done=false 时继续当前进程，不每轮调用 Organizer。
- 完成、具体阻碍、拆分、上游问题或有效停滞事件才产生交接。
- Executor 不创建兄弟任务，不自行跳到下一个节点；全局选择由 Scheduler 落实。

### R03：完成后必须交给组织者决定下一步

- 取消“已完成后先自动 activate_next 再判断是否调用 Organizer”的路径。
- 即使 B/C 已经排队，A 完成后也必须先交付给 Organizer，由它确认下一任务或修改后续计划。
- Organizer 可以选择已有就绪任务，不必重新描述全部任务；程序需有明确的选择/激活协议。不能只删掉自动推进，却让现有队列无法被选中。
- 支持创建任务、选择已有任务、继续当前未完成任务、调整/取消未执行任务、回溯和结束。可复用 action=work 并补充字段，也可增加明确 action；工具 schema、Rust 校验与提示词必须一致。
- 每次交接通过唯一身份去重，一次完成只提交一次交接。失败重试不能重复激活或重复产生副作用。
- 提交决策前，在临时状态上校验指针、依赖、权限和材料引用；校验失败不留下部分变更。

### R04：每个任务的上下文独立

Worker 输入仅包含：当前目标、必要总目标边界和共同约束、选定上游交付、当前材料、当前帧内的执行事实和错误。

- 模型消息按 node_id/revision/work_id 隔离，节点切换时重建请求。
- A 的源码调查、工具试错、推理、旧建议和局部消息保存在 A 的历史中，不自动进入 B。
- 上游交付引用绑定具体版本，并选择 B 所需字段，不能默认传全部 operations。
- Notebook 保留任务材料；Worker 只加载当前最小切片。材料库容量与模型输入预算分别管理。
- 切换任务时清空当前材料选择，再加载新任务选择。同一任务汇报一次不能导致待修改源码丢失。
- 旧结论被新结论替代时标为历史；未解决的冲突显式表达，不能将矛盾结论同时视为现行事实。
- 原始记录继续供调试和按需读取。读取旧材料时检查当前版本，不以历史结论替代新状态。

### R05：输入输出交付与实现检查闭环

- Organizer 派发的任务应明确到 Worker 可以直接行动；必要事实缺失时安排具体调查任务，材料足够时直接实现。
- Worker 输出包含 summary、exported_data、必要材料和结论引用，以及 completed/blocked/need_split/upstream_problem 等交接结果。
- upstream_problem 指向具体节点交付、版本和问题字段，Worker 不自行回溯。
- 文件改动和检查结果由程序记录；write_check 需真实写入且声明的当前版本检查通过。
- 检查失败由 Worker 在同一进程内实现 → 检查 → 修复 → 检查。需要扩大范围或上游修复时才交接。
- 满足完成条件后结束当前帧，不追加“我马上结束”“再确认一次写入”的空轮次。
- 普通知识回答有一个 Flow 节点即可，不强制读代码、拆阶段或运行检查。
- Organizer 最终答复基于实际交付，不能把编译通过等同于任意大功能完成，不能漏掉用户要求的剩余部分。

### R06：回溯后全部旧下游废弃，重新布置

必须支持明确的 revisit 协议。举例：

```text
原计划：A → B → C → D
在 C 回溯到 A：旧 B、C、D 全部废弃
新计划：A@2 → E → F，由 Organizer 重新布置
```

- 以当前有效计划中的明确顺序确定回溯范围，不仅看创建时间或直接依赖。
- 目标之前的任务保留；目标之后所有旧任务退出有效计划，包括待执行、暂停、正在执行和已完成的任务。
- 总目标父节点保留；新计划完成前不能用旧下游交付把总目标标为完成。
- 新下游使用新的实例 ID，不恢复旧下游队列、局部上下文和完成标记。目标相同也属于重新派发。
- 废弃任务不参与 all_done、依赖满足、交付汇总和 Worker 默认输入。
- 当前调用在边界结束或被取消，副作用结果归档后再提交回溯；旧计划晚到结果只归档。
- 不维护“修好 A 再回到旧 B”的恢复栈。
- 任务废弃与文件撤销分别处理。旧修改、服务等真实副作用仍记录，重新安排的任务以当前真实工作区状态为准；需要恢复时明确范围。

### R07：Flow 保留灰色废弃节点和路径

- Flow 的显示集合包括有效任务和废弃历史任务；调度的执行集合仅包含有效任务。
- 废弃节点和原有连线默认保留在画布，变灰并标注“已废弃”；作废前已经完成的节点也使用废弃样式。
- 节点详情保留原输入、输出、工具结果、作废前状态、原因、来源和版本，可查看但不可继续执行。
- 新任务形成新的可见路径。不得按相同标题覆盖或合并旧任务实例。
- replaceCurrentTurn 和 flow/plan 重建必须保留废弃节点及连线；刷新页面仍能重建完整路径。
- 同时显示目标归属边和 A → B → C 的执行依赖边，区分两种关系。
- 布局尽量保留旧路径位置，避免回溯时所有节点重新跳动。执行高亮只能属于当前有效任务。

### R08：问题来源、回溯目标和返工记录可观察

- 展示“发现问题的节点 → 回溯目标”的事件或连线，能查看原因及相关输出版本。
- 汇总节点被回溯次数、发现上游问题次数和最近原因，按事件 ID 去重。
- 连带废弃不是节点自身出错；不能把 B/C/D 全部统计为缺陷节点。
- 区分计划调整、怀疑上游问题和已确认问题。回溯次数表示返工频率，不能直接当作已确认缺陷数。
- 调试模式可按执行版本查看真实模型请求及交付；非调试界面仍保留 Flow 的任务与废弃标识。

### R09：持久化、取消与恢复

- 指针、有效队列、任务版本、计划版本、交付和废弃记录应组成可恢复的状态。
- 一次交接原子提交状态和必要事件，避免指针属于 B 而输入还是 A。
- 对继续当前会话提供明确的恢复入口；只标记 interrupted 或新建默认 Scheduler 不算恢复实现。
- 重启恢复使用最后已提交状态。执行中的写入、后台服务和工具先核对实际结果，不盲目重放。
- 已知结果属于旧实例时归档到旧实例，不能影响新计划。取消沿用现有机制，不杀死无关项目进程。

### R10：控制空转与 Observer 耦合

- 无进展检查在新的有效窗口触发，不超过阈值后每轮调用 Organizer。
- 进展根据真实变化、新检查或实质新信息判定；改写汇报、换材料 ID、修改约束文字不能无限清零。
- 相同信息下反复 continue/revisit 必须有界，最后交付明确阻碍及已完成部分。
- Observer 建议被读取并落实为当前输入、后续任务调整或有理由的处理记录；不要求 Worker 为回复建议单独空转。
- Observer 不直接选择执行节点，不批准普通检查，不重新打开已完成任务；需要回溯时由 Organizer 决策。

## 五、建议实施批次

1. R01/R02/R03：身份、执行器与完成交接，先跑通 A → B。
2. R04/R05：最小上下文与输入输出，确保 Worker 能独立完成当前任务。
3. R06/R09：回溯截断、版本及可恢复状态。
4. R07/R08：灰色旧路径、回溯信息和请求归属。
5. R10 与完整验收：检查重复交接、重复读取和空转。

主要文件：`work_scheduler.rs`、新增 `work_executor.rs`、`work_organizer.rs`、`flow_tree.rs`、`agent_service.rs`、`task_notebook.rs`、`worker_work_state.rs`、`request_context.rs`、相关 prompts、前端 model/FlowView/TaskNode 及样式。必要时复用数据库与事件机制。

## 六、验收标准

| 场景 | 合格结果 |
| --- | --- |
| 初始排队 A/B/C | A 完成后 Organizer 接收其结果并决定 B；没有自动跳过交接 |
| 简单技术问答 | 单节点回答，不无故调查项目 |
| 实现与检查 | 同一进程完成普通修复，成功后不反复查写入或 diff |
| 当前进程 B | 请求只含 B 的过程及选定上游交付，没有 A 的试错历史 |
| C 回溯到 A | 旧 B/C/D 全部灰色保留，退出执行；重新从 A 安排 E/F |
| 下游已完成或无直接依赖 | 位于回溯点之后仍被废弃，不参与完成判断 |
| 刷新 Flow | 灰色节点、旧连线、原因和版本仍可查看 |
| 重复或晚到事件 | 不重复计数，不覆盖新结果，不激活旧计划 |
| 回溯统计 | 能区分发现节点、返工目标和连带废弃，避免误判故障来源 |
| 中断、重启、继续 | 恢复单一指针和提交状态，不盲目重复写入、启动服务 |
| 无新事实的持续调查 | 有界交接和明确阻碍，不被汇报改写无限续命 |
| 缺少必要工具 | 交付具体能力缺口和实际部分结果，不反复搜索工具替代方案 |

至少提供正常 A → B → C、回溯 A@2 → E → F、直接问答三类实际流程记录。记录节点输入输出、组织者决策、调度指针、实际请求及 Flow 展示；覆盖失败、恢复和旧事件边界。报告工具调用及组织者调用次数，并解释交接原因。

只更新提示词、添加没有实际调用的 Executor 文件、扩展 UI 状态枚举，均不算完成。编译通过也不能代替这些行为验收。
