# 代码工作流程

从当前需求、项目规范、已提供的任务状态和已有结果开始，定位相关代码、修改并验证。已有材料直接复用；只有缺少具体信息时才读取对应文件、任务板或历史，避免把准备工作变成固定的工具调用仪式。已加载的规范和技能直接复用。

按需求定位代码、修改并验证，工具结果回到同一上下文后继续决定下一步。Flow 按实际模型请求和工具执行自动记录，不需要另行创建、启动或完成流程节点。开工前建议记录简洁的主任务；已有任务就承接，不重复建任务。用户只要计划时，提供计划后结束本轮。

相关文件、材料、工具结果和实际验证结论通过当前上下文与稳定引用承接。只有可独立处理且值得委派的工作才使用已提供的协作工具，避免无谓分支。用户明确划定的职责与授权仍须遵守，保留工作区中他人的修改。

按实际影响运行测试，检查成功输出再汇报。委派代码工作时划清文件职责；验收 Git 委派须先 `inspect_agent_changes`，再按已检查的 head 调用 `merge_agent_result`，检查集成结果并用实际证据记录 `review_agent_result`。分支结束不等于交付通过。

## 按功能追踪源码

需要了解功能调用关系时使用 `read_code_flow`。先读取功能目录，再选择有关的 `feature_id`；需要局部证据时指定 `node_id`，只读该节点的源码与直接依赖，不反复取回整图。当前结果仍在上下文时直接使用；缺少正文时按稳定资产引用回读。

功能分组、职责和 `entry/unit/shared` 标记属于人或 AI 的架构声明。根据实际源码判断哪些职责应独立、哪些公共能力应集中。宿主只解析显式声明和调用事实，不替你判断耦合，也不根据用户关键词选择功能。

关注同一职责是否有多个实现入口，以及是否存在绕过公共入口的读取或写入。共享能力应有明确的接口和唯一职责归属；一个功能内部可以有多个方法。分流、汇合和交叉线帮助定位疑点，不能仅凭连线数量认定重复代码或过度耦合。

调用边附文件、位置和版本。边界与未解析调用仍是证据的一部分。首版是 Rust 静态语法关系，宏和动态派发未解析；不要宣称完整编译器关系或运行时覆盖。

根目录 `code-flow.json` 保存显式功能层级和方法绑定。没有声明时，根据源码建立所需功能的最小声明，再使用工具；修改源码后刷新相关图，并同步确有变化的职责声明。源码缺失、歧义和版本冲突须依据实际代码处理。

节点提供测试入口。根据输入输出和真实依赖选择局部测试，再验证受影响的上下游。通过已有执行工具运行节点 `test_entries.argv`；确认实际执行了目标测试，依据真实输出报告结果。测试命令和测试源码存在不代表测试已经通过。

不再需要时可调用 `unload_skill` 隐藏本技能工具。已加载技能跨步骤和用户轮次继续可用；卸载或包版本变化后需要重新加载。加载不扩展执行权限。
